## Анимации (правило, введено 09.07.2026)

**Требование владельца: «все будущие анимации делать именно так» — обязательно для
ЛЮБОЙ новой анимации в приложении, без исключений.**

### Стандарт

- **Длительность**: 250–300мс (эталон — `280ms`). Раньше в проекте использовались
  разные значения ~150–180мс — визуально ощущались резко/«дёргано». Дольше 300мс —
  уже ощущается медленно и тормозит работу с интерфейсом, короче 250мс — не успевает
  прочитаться как плавное движение.
- **Кривая**: `cubic-bezier(0.32, 0.72, 0, 1)` — классический iOS/macOS деселерейт
  (быстрый разгон, мягкое торможение к концу). Не использовать линейные (`linear`) или
  стандартные CSS (`ease`, `ease-in-out`) кривые для панелей/шторок/значимых переходов.
- **Переменные**: обе величины заданы в `app/globals.css` как CSS custom properties в
  `:root`:
  ```css
  --anim-duration: 280ms;
  --anim-ease: cubic-bezier(0.32, 0.72, 0, 1);
  ```
  Новая анимация обязана ссылаться на `var(--anim-duration)` / `var(--anim-ease)` —
  **не хардкодить** свои мс/кривые в компоненте или отдельном keyframe-классе. Если
  нужно поменять общий тайминг приложения — правка в одном месте (`globals.css`)
  применяется ко всем анимациям сразу.
- **Исключение — ховеры**: наведение курсора (hover-состояния кнопок/ссылок/строк
  таблицы, `.hover-reveal`) должно оставаться быстрым (~150мс, значение по умолчанию
  `transition-colors`/`duration-150` из Tailwind) — на них правило НЕ распространяется.
  Замедление отклика на hover ощущается как «тормозит интерфейс», а не как приятная
  анимация.
- **Готовые классы** (использовать вместо новых самописных):
  - `.slide-panel-in-right` / `.slide-panel-out-right` / `.slide-panel-in-left` /
    `.slide-panel-out-left` — выезд/выезд обратно правых и левых панелей.
  - `.slide-backdrop-fade` — плавное появление/скрытие затемняющей подложки под
    панелью (используется в компоненте `<SlideBackdrop>`, `components/ui/SlideBackdrop.tsx`,
    и подключается напрямую там, где вёрстка подложки нестандартна — см. комментарии
    в файле).
  - `.metric-compare-col-enter` / `.metric-compare-col-exit` — плавное появление/
    схлопывание колонок сравнения в `ReportTable.tsx`.
- **JS-таймеры**: если анимация управляется и CSS, и JS-таймером (например,
  `COMPARE_CLOSE_MS` в `features/reports/ui/ReportTable.tsx`, который держит колонки
  смонтированными на время fade-out), JS-константа должна численно совпадать со
  значением `--anim-duration` (JS не умеет читать CSS-переменные напрямую) — при
  изменении длительности в `globals.css` обязательно поправить и такие константы.
- **`prefers-reduced-motion: reduce`**: анимации должны отключаться (см. media-query
  в конце `globals.css`) — это правило не отменяется новым стандартом.

### Как добавить новую анимацию

1. Не писать `animation: my-thing 150ms ease-out` — использовать
   `animation: my-thing var(--anim-duration) var(--anim-ease)`.
2. Для CSS-переходов (`transition`) — `transition: <property> var(--anim-duration) var(--anim-ease)`,
   не `duration-150`/`duration-200`/произвольные мс через Tailwind-утилиты.
3. Если это hover/фокус-отклик — можно и нужно оставить быстрым (не подключать эти
   переменные).

## Панели с сохранением (правило, введено 09.07.2026/2)

**Требование владельца: при ЛЮБОМ закрытии панели с несохранёнными изменениями —
клик по затемнению (`SlideBackdrop`), крестик (`PanelCloseTab` или крестик в
доке/на мобиле), Esc — обязателен диалог подтверждения. Без исключений для панелей,
у которых есть отдельная кнопка «Сохранить».**

### Как отличить панель, которой это правило нужно

- **Есть кнопка «Сохранить»**, и часть состояния панели — «черновик», который
  реально теряется при закрытии без клика по ней (пример: `HighlightEditor` —
  режим «Пороги»/значения порогов/цвет «выше последнего» не попадают в отчёт, пока
  не нажать «Сохранить»). → правило подключить.
- **Всё применяется мгновенно** через колбэки-пропсы прямо в состояние
  родителя, кнопки «Сохранить» нет вовсе (пример: `ReportSettingsPanel` — Фильтры/
  Вид, `Seg`/toggle-контролы `FiltersFields`/`ViewSettingsFields`). → правило НЕ
  подключать, закрыть панель нечем «уронить». Отметить это явно комментарием в
  компоненте (см. `ReportSettingsPanel.tsx`), чтобы через полгода кто-нибудь не
  добавил диалог туда «по аналогии» без реальной необходимости.
- Панель может быть **смешанной**: часть полей мгновенная, часть — за «Сохранить».
  `isDirty` считает ТОЛЬКО вторую часть (иначе диалог будет всплывать по любому
  чиху, включая уже сохранённые действия — ложная тревога).

### Механизм

- `lib/hooks/useUnsavedGuard.ts` — хук состояния диалога: `requestGuardedClose(isDirty, close)`
  вызывать вместо прямого `requestClose()`/`onClose()` на ВСЕХ триггерах закрытия
  панели (подложка, `PanelCloseTab`, крестик, Esc). Если `isDirty` — не закрывает
  сразу, поднимает диалог и запоминает `close` для отложенного вызова.
- `components/ui/UnsavedChangesDialog.tsx` — сам диалог, построен на золотом
  стандарте `<Modal>` (`components/ui/Modal.tsx`, Radix Dialog), не самописный
  fixed-оверлей. Заголовок «Есть несохранённые изменения», три кнопки строго в этом
  порядке: **«Сохранить»** (primary, accent-заливка — вызывает ту же функцию
  сохранения, что и кнопка «Сохранить» самой панели) / **«Не сохранять»** (текст
  `--color-negative`, закрывает панель, черновик отбрасывается) / **«Отмена»**
  (нейтральный текст, просто закрывает диалог — панель остаётся открытой).
- `isDirty` считает КАЖДАЯ панель сама (хук об этом не знает) — сравнением
  локального черновик-состояния с уже сохранённым (`initial`-пропом/бейзлайном на
  момент открытия/последнего Save), см. пример в `HighlightEditor.tsx`.
- Esc теперь обязателен у ЛЮБОЙ такой панели, даже если раньше его не было
  (`HighlightEditor` до этой правки закрывался только по подложке/крестику) —
  добавить `useEffect` с `window.addEventListener('keydown', ...)`, вызывающий
  тот же `requestGuardedClose`, что и остальные триггеры.

## Режимы запуска (`useAppMode`) — правило, введено 02.08.2026 (задача 2764)

**Требование владельца («го» на аудит `owners-inbox/analsteroid-mobile-readiness.md`):
ЛК должен быть адаптирован под каноны мобильного приложения и доступен как отдельный
URL, не только как локальное приложение внутри Битрикса — «Система должна сама
понимать, как её открыли, и подстраиваться». Значит нужен ОДИН механизм определения
режима, а не россыпь частных проверок по компонентам.**

### Контракт

`lib/hooks/useAppMode.ts` — единственное место, которое знает, ГДЕ и КАК запущено
приложение. Любой новый UI, которому нужно вести себя по-разному в зависимости от
режима, ОБЯЗАН спрашивать этот хук, а не писать свою проверку
`window.self`/`matchMedia('display-mode')`/`navigator.standalone`/User-Agent. Если
подходящей логики в хуке не хватает — расширять сам хук, не городить локальный
дубль рядом (иначе ровно то, от чего хук должен избавить, произойдёт снова: логика
режимов расползётся по компонентам и перестанет быть единой правдой).

```ts
import { useAppMode } from '@/lib/hooks/useAppMode';

const { mode, isMobileLayout, isBitrixIframe, isStandalone } = useAppMode();
```

### Четыре режима — иерархия, не независимые флаги

1. **`bitrix-iframe`** — внутри `<iframe>` портала Битрикса (`window.self !== window.top`).
   Определяется РАНЬШЕ всего и перекрывает остальное: неважно, с телефона открыли
   портал или с десктопа (мобильное приложение Битрикс24 тоже рисует iframe) —
   поведение внутри портала должно быть предсказуемым независимо от устройства.
   На практике это ТОЛЬКО роуты `app/(embed)/`, у них нет `AppShell` вовсе (свой
   хром даёт портал).
2. **`standalone`** — установлено на домашний экран / открыто как отдельное
   PWA-приложение без адресной строки браузера (`display-mode: standalone` или
   легаси `navigator.standalone` на старом iOS Safari).
3. **`mobile`** / **`desktop`** — обычный браузер (вкладка/таб), различаются по
   ширине вьюпорта (`<768px`, тот же порог, что `useIsMobile()`/Tailwind `md:`).

**`isMobileLayout` — отдельный флаг, не производная от `mode`.** Для решений про
раскладку («нижний таб-бар вместо сайдбара», «bottom-sheet вместо модалки», доп.
отступы) нужен именно он, а не `mode === 'mobile'`: `standalone` почти всегда узкий
(обычный случай — установка на телефон), но теоретически может быть и широким (PWA,
установленное на десктопном Chrome). `mode` отвечает на вопрос «откуда и как открыто
приложение», `isMobileLayout` — на вопрос «какая раскладка нужна прямо сейчас».

### Что уже построено на этом механизме (примеры для новых компонентов)

- `components/bitrix/BitrixFrameFit.tsx` — раньше сам проверял
  `window.self === window.top`, теперь читает `isBitrixIframe` из хука.
- `AppShell`/навигация (см. план мобильной оптимизации) — по мере доработки бокового
  меню/нижнего таб-бара источник решения «что показать» — этот хук, а не отдельный
  `md:hidden` без единой логики (там, где достаточно чистого CSS-брейкпоинта без
  ветвления DOM — по-прежнему предпочитать CSS, правило 8 CLAUDE.md; хук — когда
  нужна структурно другая разметка ИЛИ признак недоступен CSS в принципе, как
  `bitrix-iframe`).

### Ловушка SSR (важно при написании нового кода на хуке)

`useAppMode` построен на `useSyncExternalStore` (SSR-safe, как `useIsMobile`) — на
сервере и в момент гидрации все три признака (`isBitrixIframe`, `isStandalone`,
`isMobileLayout`) возвращают безопасный дефолт (`false`/`desktop`), а РЕАЛЬНОЕ
значение приходит одним рендером позже, сразу после гидрации. Если значение из хука
попадает в зависимости `useEffect` — этот эффект обязан слушать его в
`deps`-массиве, а не захватывать значение первого рендера в пустом `[]` (грабля,
на которую наступили и тут же поправили при рефакторинге `BitrixFrameFit.tsx` —
с пустым `[]` эффект навсегда захватил бы устаревший `false` и BX24 внутри
настоящего Битрикса никогда бы не подгрузился).

## URL-адресуемость экранов (`useUrlState`) — правило, введено 03.08.2026 (задача 2824)

**Требование владельца (Серёга): «Внутри всего сервиса каждый экран или даже
открытые настройки должны иметь понятный и воспроизводимый урл. Если я кидаю ссылку
на открытые настройки коллеге, у него должны открываться его настройки. Или
"недостаточно прав", если нет прав на просмотр».**

Аудит `owners-inbox/analsteroid-url-addressability-audit.md` (задача 2822) нашёл, что
из 58 заснятых экранов только 3 переживают перезагрузку без потерь (там просто нечего
терять), и что состояние ПОЧТИ ВЕЗДЕ жило в обычном `useState` — фильтры, период,
вкладки, поиск, сортировка, открытые модалки исчезали при `F5` или пересылке ссылки.
Единственным исключением была вкладка ЛК менеджера (`?tab=` в
`ManagerCardPage.tsx`, задача 2764) — точечное решение без обобщённого механизма.
Этот раздел документирует общий механизм (задача 2824, волна 1 плана), реализованный
1:1 по контракту из аудита.

### Контракт

`lib/hooks/useUrlState.ts` — единственное место, которое знает, КАК состояние
экрана превращается в query-параметр и обратно. Любой новый фильтр/период/срез/
вкладка/поиск, который имеет смысл переслать ссылкой, ОБЯЗАН идти через этот хук,
а не через локальный `useState` с ручной синхронизацией в URL — иначе снова
разойдётся по компонентам, как уже было до этой задачи.

```ts
import { useUrlState, enumParam, dateRangeParam } from '@/lib/hooks/useUrlState';

const [dealScope, setDealScope] = useUrlState('dealScope', enumParam(['primary', 'repeat', 'all'], 'all'));
const [period, setPeriod] = useUrlState('period', dateRangeParam(initialPeriod)); // 'replace' по умолчанию
const [tab, setTab] = useUrlState('tab', { ...enumParam(TAB_KEYS, 'dashboard'), mode: 'push' });
```

Готовые фабрики `parse`/`serialize` в том же файле — `stringParam`, `enumParam`,
`boolParam`, `intParam`, `listParam` (список через запятую, порядок сохраняется —
важно для полей вроде набора метрик отчёта), `dateRangeParam` (пара ISO-таймстампов
через запятую). Для модалок — облегчённый `useUrlModal()` (`?modal=<key>`, не нужно
городить полноценный `useUrlState` на каждую панель). Для атомарной правки НЕСКОЛЬКИХ
параметров одним вызовом (например «сбросить все фильтры») — `useUrlStateBatch()`.

1. **URL — источник правды, не зеркало.** Значение читается из `useSearchParams()`
   на каждый рендер, параллельного `useState` для синхронизации нет — та же
   дисциплина, что уже применена к `useAppMode`/`useUnsavedGuard` (один хук, не
   россыпь локальных копий).
2. **Значение, равное дефолту, не пишется в URL** — сравниваются СЕРИАЛИЗОВАННЫЕ
   строки (`serialize(value) === serialize(default)`), поэтому базовая ссылка на
   отчёт «по умолчанию» не обрастает шумом `&key=default`.
3. **`push` vs `replace` решает вызывающий экран**, не хук (`mode` в опциях,
   дефолт — `replace`). Смысловой шаг (открытая сущность/таб — «назад» должен на
   него возвращать) — `push`. Непрерывная донастройка (текст поиска, фильтр, драг
   слайдера — не должны засорять history каждой буквой) — `replace`.
4. **Батч без гонок.** Несколько `setValue()` из РАЗНЫХ `useUrlState()`/
   `useUrlStateBatch()` в одном синхронном обработчике (например «сбросить все
   фильтры» — пять полей одним кликом) копятся в общей микрозадачной очереди и
   уходят ОДНОЙ навигацией — иначе каждый вызов читал бы один и тот же снимок
   `searchParams` текущего рендера и последний вызов молча побеждал бы остальные.
5. **SSR-дисциплина.** Значение — чистая производная от `useSearchParams()`
   (server-safe в Next по построению), никакого захвата в `useEffect` + `useState`
   по пустому `[]` — та же ловушка, что уже поймали и объехали на `useAppMode`
   (см. раздел выше), не нужно наступать на неё второй раз на другом хуке.
6. **Malformed/устаревший URL не роняет страницу.** Если `parse()` бросает
   исключение (ручная правка адреса, ссылка на удалённое значение enum) — тихий
   откат к дефолту, как будто параметра не было вовсе.

### Приоритет источников при монтировании (важно для экранов с localStorage/пресетами)

Некоторые экраны ДО этой задачи уже восстанавливали состояние из другого источника
на монтировании — например `SalesReportPage.tsx` хранит полный снимок открытой
вкладки отчёта в `localStorage` («вкладки отчётов», задача 01.08) и хендлит пресет
сохранённого отчёта из БД (`saved_reports`). Оба источника теперь ДОЛЖНЫ уступать
явному query-параметру в URL на самом первом монтировании — иначе диплинк вида
`/sales/saved/<id>?dealScope=primary` тут же затирался бы обратно сохранённым
значением тем же эффектом, который его восстанавливает, и вся адресуемость теряла
бы смысл. Паттерн (см. `SalesReportPage.tsx`): держать `useRef` со снимком
`searchParams` и проверять `ref.current.has(key)` ПЕРЕД применением значения из
пресета/восстановленного снимка — но ТОЛЬКО на первом restore при монтировании;
последующие явные действия пользователя (переключение на другую открытую вкладку,
выбор другого пресета) применяют своё состояние целиком, URL после них обновляется
ПОД них, а не наоборот.

### Готовые примеры

- `features/manager-card/ui/ManagerCardPage.tsx` — вкладка ЛК (`?tab=`), первый
  прецедент в проекте, теперь можно переписать на `useUrlState` при следующей
  правке файла (не переписано в рамках 2824 — работает и так, трогать без нужды
  не стали).
- `features/badges/ui/RewardsSettingsPage.tsx` — 12 вкладок «Настройки → Награды»
  (`?tab=`, `push`), прямой аналог `ManagerCardPage`.
- `features/reports/ui/SalesReportPage.tsx` — период, сравнение, срез сделок/
  клиентов, группировка, набор метрик, поиск, сортировка, доп.фильтры (`replace`).
  Формат-настройки просмотра (зебра, границы, точность, дрилл-даун-детали) НЕ
  мигрировали — это персональные предпочтения показа, не «какой отчёт открыт», та
  же граница, что уже проведена для `viewPrefs` (живёт в `localStorage`, не в БД
  и не в URL, см. `SECRETS_AND_STORAGE.md`).

### `<AccessDenied>` — «недостаточно прав», а не молчаливый редирект/404

`components/ui/AccessDenied.tsx` — второй кусок того же требования владельца
(«или "недостаточно прав", если нет прав на просмотр»), отдельный от URL-хука, но
с тем же принципом canon-компонента: один `<AccessDenied reason="..."/>` вместо
россыпи чуть разных `<div className="p-6 text-sm...">` по каждому разделу.
Применять вместо `redirect()`/`notFound()` в ЛЮБОМ месте, где причина отказа —
именно нехватка права (сессия есть, конкретного `hasPerm`/`isSuperadmin` не хватает).
Случай «сессии нет вовсе» по-прежнему `redirect('/login')` — это не про права,
это про то, что заходить нужно залогиненным, ведёт себя одинаково честно во всём
приложении и трогать не нужно. Случай «сущности с таким id правда не существует»
(soft-deleted, опечатка в ссылке) — по-прежнему `notFound()`, это ЧЕСТНЫЙ 404, не
маскировать его под «нет прав» тоже неверно (см. `/sales/saved/[id]/page.tsx` —
там оба случая различены явно).
