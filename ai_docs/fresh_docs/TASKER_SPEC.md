# Задачник — ТЗ (черновик на согласование, 23.11)

Статус: **подтверждено владельцем 23.11 с дефолтами** (ответы на вопросы — дефолты в скобках).
Открыто у владельца: ID группы «Задачник» в Битриксе и право `calendar` основному вебхуку (`BITRIX_WEBHOOK_URL`).

## Зачем

РОП/директор видит в отчёте просадку показателя у менеджера → в два клика ставит
задачу «подтянуть X до среднего», с цифрами-доказательствами и рекомендациями.
Задача живёт в Битриксе (отдельный проект), а в Монолитике — доска, неделя, сегодня
и **автозамер результата**: на контрольную дату система сама пересчитывает показатель
и ставит вердикт. Без замкнутой петли это была бы обёртка над задачами Битрикса.

## Сценарий

1. Отчёт «По менеджерам» (`ReportTable`) → у строки менеджера кнопка «Поставить задачу»
   (рядом с иконкой карточки; на таче видна). Ещё вход — шапка карточки менеджера и
   кнопка «Новая задача» в самом Задачнике. Можно отметить **несколько менеджеров** →
   одна форма, снимок у каждого свой.
2. Форма (Drawer/bottom-sheet):
   - Вверху две кнопки (правка 23.11): **«Теория — Будковский»** (исполнитель — тренер,
     `tasker_settings.trainer`, по умолчанию 2054) и **«Практика — работаю сам»** (исполнитель —
     постановщик: выбранный в поле «Постановщик» РОП или сам нажавший). Поля «исполнитель» нет.
   - **Показатель** — из белого списка «прокачиваемых» метрик (с направлением
     «больше = лучше / меньше = лучше»); по умолчанию — колонка, у которой нажали
     (если в белом списке).
   - **Снимок** (считается автоматически, только для чтения):
     значение менеджера за период отчёта · среднее по отделу за тот же период ·
     собственное среднее менеджера за 6 полных месяцев до периода.
   - **Цель** — по умолчанию среднее по отделу, можно поправить руками.
   - **Шаблон рекомендаций** по метрике (2–3 готовых текста) → редактируемое тело.
   - **Заказчики из канбана повторных** (галочка): у менеджера с открытым окном
     (22 дня) и ровно 1 отгрузкой — уходят чек-листом в задачу + привязкой к CRM.
   - **Срок**, **длительность** (по умолчанию 30 мин), **слот сессии** (дата/время),
     **контрольная дата замера** (по умолчанию срок + 7 дней — «смотрим неделя через неделю»,
     правка 23.11; руками можно поменять).
3. Создаётся задача в Битриксе — **одна задача = один менеджер** (выбрали троих — три задачи):
   - проект «Задачник» (`GROUP_ID` = 125),
   - **ответственный (`RESPONSIBLE_ID`) — РОП/постановщик («Практика») или тренер («Теория»)**,
     не менеджер (правка 23.11: Задачник — инструмент РОПа). Менеджер — в описании и
     участник события календаря, наблюдателем НЕ ставится. Наблюдатели (`AUDITORS`) —
     директор по продажам, РОП менеджера (если он не исполнитель и не постановщик) и нажавший,
     если ставил «от имени» другого. Постановщик — выбранный в форме или нажавший,
   - `TAGS` = метрика (тема), `TIME_ESTIMATE` = длительность,
     `START_DATE_PLAN/END_DATE_PLAN` = слот, `DEADLINE`, **`TASK_CONTROL=N`**,
   - описание (BB-код): менеджер, формат (теория/практика), цель, снимок трёх значений,
     рекомендации, ссылка в Монолитику,
   - тип хранится в `tasker_tasks.kind` (`theory|practice`, по умолчанию practice; у задач до 23.11 исполнитель
     — менеджер), исполнитель — `executor_bitrix_id` (= RESPONSIBLE_ID), наблюдатели — `auditor_ids` (миграция 279).
   - дубль = открытая задача по той же метрике **того же типа**: теория и практика по одной теме
     ставятся двумя задачами.
4. Дальше: исполнитель проводит работу и **завершает задачу сам** — кнопкой «Завершить» с
   обязательным полем **«Что сделано»** (≥ 10 символов: «обработано 14 сделок, проверены брони…»).
   Текст уходит комментарием в задачу Битрикса и в `tasker_tasks.done_note`, виден на карточке и
   директору. Подтверждения директора нет (колонки «Ждёт контроля» нет). Задача уходит
   «На замере»; на контрольную дату — автозамер и вердикт («достигнуто / рост, не дотянул /
   без изменений / мало данных») комментарием в задачу. Ошибочное завершение откатывается из
   карточки («Вернуть в работу»), пока нет вердикта; после вердикта — только новая задача.
   Менеджер видит задачи про себя **только на чтение**: статус меняют исполнитель или постановщик
   (РОП/директор менеджера с правом `action.tasker.assign`).

## Темы и «умное расписание»

- **Тема** (+ группа: конверсии / чеки / активность / повторка / товарные группы) — тег в Битриксе, группировка
  и фильтр на доске, группировка очереди тренера. С 23.11 (миграция 282) темы **заводят руководители** в
  «Задачник → Шаблоны» (право `action.tasker.templates`, админ — и так). Два типа:
  - **Показатель** — любая метрика каталога отчётов (`lib/metrics/catalog.ts`), не только 10 стартовых. Поля:
    короткое название, группа, «больше/меньше — лучше», формат. Снимок/замер — ячейка отчёта «По менеджерам», как раньше.
    Правило «мало данных» по знаменателю (< 5) есть только у стартовых 10 (у новых — «нет значения»).
  - **Материалы по товарной группе** — группа из справочника отчёта «По товарным группам» (`sa.product_groups`,
    шкала kc). Замер (выбирается при создании): **сумма продаж группы** у менеджера (₽) или **доля группы в его
    продажах** (%). Считается тем же отчётом «По менеджерам» с фильтром `productGroupId` (как дрилл-даун из
    «По товарным группам» в менеджера), метрика «Сумма продаж» (`all_sales_amount`); доля — второй прогон без
    фильтра. Продавал, но не эту группу → 0, а не «мало данных»; не продавал вовсе → «мало данных».
  - Под темой — варианты инструкции (шаблоны). Удаления темы нет — **архив**: из формы пропадает, старые задачи и
    замеры с ней живут. Хранение — та же таблица `tasker_metrics` (на неё ссылаются задачи), id темы-показателя =
    id метрики, id товарной группы = `pg_<id>_<amount|share>`.
- **Сессия** = встреча РОПа по одной теме. При создании задачи форма подсказывает:
  «У вас уже есть сессия по CR ППП в четверг 11:00 — добавить туда?». Однотипные задачи
  складываются в одну сессию, а не в N встреч. Длительность сессии = 30 мин +
  15 мин на каждого следующего менеджера.
- **Календарь Битрикса**: сессия = одно событие `calendar.event.add` в календаре исполнителя
  (РОПа или тренера; сессия собирается по исполнителю), участники — менеджеры, ссылки на задачи
  в описании. Задача со слотом **без сессии** — своё событие в календаре исполнителя с менеджером-
  участником (`features/tasker/engine/taskCalendar.ts`, op `task_calendar`; правка 23.11 п.10:
  менеджер узнаёт о встрече из календаря и уведомления). Слот сняли — событие удаляется.
- **Действия у сессии** (миграция 283, `PATCH /api/tasker/sessions/:id`): «Провёл» — отметка (кто/когда),
  задачи не закрывает; «Перенести» — новое время/длительность → слоты задач, их плановые даты и событие
  календаря в Битриксе (через outbox), занятость в новое время — предупреждением. Могут исполнитель сессии,
  его директор, админ. Кнопки — в блоке сессии «Недели»/«Сегодня». Требует права `calendar` у
  вебхука (сейчас нет — см. вопросы). Пока прав нет — задача всё равно получает
  плановые даты и видна в планировщике задач Битрикса.
- Фаза 2: подбор свободного слота по занятости (`calendar.accessibility.get`).
  Автоперепланирования не делаем.

## Задачник в Монолитике (раздел `/tasker`)

Три вида, общий фильтр (РОП / менеджер / тема / мои-поставленные-наблюдаю):
- **Доска** — колонки: Новая · В работе · Завершена · На замере (ждёт контрольной даты) ·
  Вырос · Не вырос (правка 23.11; «Ждёт контроля» убрана, статус 4 старых задач читается как
  завершённая). Перетаскивание = смена статуса в Битриксе; бросок в «Завершена» открывает
  карточку с «Что сделано».
- **Неделя** — 5 рабочих дней, задачи и сессии по плановому слоту/сроку.
- **Сегодня** — повестка: сессии дня, просроченное, сроки сегодня, замеры сегодня.

Карточка задачи (Drawer): снимок → текущее значение (живое) → вердикт, чек-лист
заказчиков, ссылка «открыть в Битриксе».

Видимость: менеджер видит задачи про себя (только чтение); РОП — своих менеджеров; директор —
свой филиал; админ — всё (`getSessionScope` / `canSeeManager`). Плюс — независимо от зоны —
задачи, где ты исполнитель (тренер видит свои «теории»), постановщик или наблюдатель
(`auditor_ids`, AUDITORS Битрикса).

## Обучения (расписание тренера)

Сотрудник-тренер (сейчас Будковский) систематически проводит обучения менеджеров.
- Раздел `/tasker/trainings` (вкладка Задачника): **расписание обучений видят все**.
- Создавать/править/отменять события может **только тренер** — право
  `action.tasker.trainings.manage` (выдаётся личным исключением, в код имя не зашиваем).
- Событие: тема, описание/программа, дата-время начала, длительность, место/ссылка,
  лимит мест (необязательно), тренер. Серии — фаза 2.
- **РОП записывает менеджера** на конкретное событие: из карточки события («Записать
  менеджера») и из формы задачи (поле «Записать на обучение» — выбор из ближайших
  событий; ссылка на обучение — в описании задачи). Права записи — как у постановки
  задач (свои менеджеры, `canSeeManager`).
- Записанные видны в карточке события; у менеджера — в «Сегодня»/«Неделе» Задачника.
- Фаза 1b (сделано 23.11): событие в календаре тренера, записанные — участники.

### Оценка эффективности (23.11, миграция 277)

Цель владельца — фраза вида «Будковский провёл 10 менеджерам обучение по первичным продажам; связанные
показатели за следующие две недели выросли у 8 из 10».
- **Событие** привязано к показателям из белого списка Задачника (`tasker_metrics`, мультивыбор) и имеет окно
  замера «до/после» (по умолчанию 7/7 дней с 23.11, 7–90). Смена показателей/окон/даты сбрасывает сделанные замеры.
- **Запись** хранит цель: показатели (по умолчанию — показатели события) и текст «зачем отправили», кто отправил.
  Записали из задачи — цель = показатель задачи + её снимок. Ядро пишет только `tasker_tasks.training_event_id`;
  саму запись делает досинхронизация обучений (тик job `tasker` и перед чтением расписания). Нельзя записать
  (отменено/прошло/нет мест) — одна строка `enroll_failed` в журнале. Все записи/отписки/отметки — в журнале
  `tasker_training_enrollment_log`.
- **Посещаемость**: после начала события тренер отмечает «был / не был». Не отмечено — в оценку не идёт,
  в карточке «посещение не отмечено».
- **Замер** (job `tasker`, раз в 15 мин; отдельного имени в BACKGROUND_JOBS_ALLOW не нужно): после окончания окна
  «после» для каждого посетившего × показателя (показатели события ∪ цель ∪ показатель задачи) — значение за N
  дней до дня обучения и за N дней после него (сам день не входит), плюс «Итого» отдела за те же окна (контроль:
  «у менеджера +5 п.п., у отдела +1»). Вердикт — `verdictOf` автозамера ядра без цели (рост / без изменений по
  тому же порогу шума 2%); «мало данных» — знаменатель < 5 в любом из окон. Отчёт считается «глазами» того,
  кто записал менеджера (РОП), иначе создателя события. Итог человека: все показатели «мало данных» → мало данных;
  иначе выросших больше, чем без изменений → вырос.
- **Отчёты**: карточка события — «прошли 10, выросли у 8, без изм. 1, мало данных 1» + люди с замером;
  вкладка «Эффективность» — свод по тренерам, темам и показателям за период (сколько провёл, сколько человек,
  доля выросших, средний прирост против отдела) и история менеджера; блок «Обучения менеджера» в карточке задачи.
- **Видимость**: тренер и админ — все; РОП — свои менеджеры; менеджер — своё (срез сессии).
- API: `PATCH/POST` события принимают `metricIds, measureBeforeDays, measureAfterDays`; `POST /:id/enroll`
  — `goalMetricIds, goalNote`; `POST /:id/attendance {managerId, attended: true|false|null}` (тренер);
  `GET /effectiveness?from&to`; `GET /history?managerId`.
- Фаза 2: менеджер сам жмёт «Участвовать», напоминания ботом «Аналитик» (за день и за час), серии событий.

### Канбан тренера и сетка недели (23.11, миграция 281; собрание пользователей, п.6)

Модель после собрания: задача «Теория» — исполнитель тренер (`tasker_settings.trainer`, по умолчанию 2054), «Практика» —
РОП; одна задача = один менеджер. Тренер группирует индивидуальные задачи в занятия.
- **Вкладки раздела**: Неделя (по умолчанию) · Очередь тренера · Ближайшие · Прошедшие · Эффективность · Настройки (тренеру).
  Ссылка `?tab=queue|week|settings|effect` открывает вкладку.
- **Неделя** — как Excel тренера: строки — время слотов, колонки Пн–Пт (Сб/Вс — если есть слоты), в ячейке тема,
  отдел (`department_label`), фамилии записанных (чужие для РОПа — «+N»). Пустой будущий слот у тренера — «+»
  (форма обучения с подставленными временем/длительностью/местом/подписью отдела). Телефон — то же списком по дням.
- **Сетка слотов** (`tasker_training_slots`) правит тренер во вкладке «Настройки» и сохраняет целиком: день недели,
  время (МСК), длительность, название («Нулевой цикл»), место, очно, закреплённые отделы (uuid отделов продаж) и подпись
  отдела. Стартовые данные из Excel: Пн–Пт 9:30 / 10:15 / 15:00 / 16:15 по 45 мин онлайн, 11:00 «Нулевой цикл» —
  Питер, очно; Вт/Чт 16:15 — «Москва». Подпись без выбранных отделов = закрепление «на словах»: в сетке видно,
  автоматически не предлагается (вручную можно). Размер группы — там же: предлагать от 3, обычно 4, максимум 5,
  искать слот на 14 дней вперёд (`tasker_settings.training_group`).
- **Очередь тренера** — открытые задачи «Теория» (не отменены, не закрыты, без вердикта; назначенные на ещё не
  прошедшее занятие — серым внизу, на прошедшее — уходят), сгруппированные по показателю, сверху — где ждут больше.
  Видят тренер и админ — все, РОП — своих менеджеров (только просмотр).
- **Автопредложение**: по теме ждут ≥ min → ближайший слот сетки, где тренер свободен; среди них сначала те, где
  свободны все выбранные (первые по давности до «обычно берём», или отмеченные тренером), иначе — где занятых меньше.
  Занятость — `checkAvailability` ядра (календарь Битрикса + события Монолитики), слоты ближе часа не предлагаются.
  Закреплённый за отделами слот — только если все выбранные из этих отделов.
- **«Собрать занятие»** (тренер, до max человек): тема (по умолчанию — показатель), один из предложенных слотов или
  своё время, место, программа → событие обучения (показатели = показатели задач, лимит = max), запись каждого
  менеджера с целью из его задачи, `tasker_tasks.training_event_id` = событие. Кого записать не удалось — список
  с причиной, остальные записаны. Календарь тренера обновляется как при обычной записи.
- Признак «Теория» модуль обучений читает в одном месте (`trainings/engine/theory.ts`): `kind = 'theory'`,
  `executor_bitrix_id` = тренер, `done_at IS NULL` (миграция 279). До наката 279 очередь пишет «тип задачи ещё не развёрнут».
- API: `GET/PUT /api/tasker/trainings/slots`, `GET /queue`, `POST /queue/suggest {metricId, taskIds?, limit?}`,
  `POST /queue/assemble {taskIds, startsAt, durationMin, title, place?, slotId?, departmentLabel?}`.
- Исторический журнал Excel (кто когда был) не переносили: фамилии не сопоставляются с Bitrix ID однозначно,
  в комментариях — оценки людей.

## Регулярные собрания (планёрки, разборы) — 23.11

Дефолты задачи владельца (не уточнял — приняты так, правится настройкой/кодом):
- **Создают** РОП / директор / админ (`action.tasker.assign`). **Организатор** — создатель; директор/админ может
  выбрать другого (в своей зоне). Править/отменять — создатель, организатор или их руководитель (зона `canSeeManager`).
- **Участники** — отделы целиком (uuid `sa.departments`, с поддеревом; состав пересчитывается сам) и/или люди.
  Пикеры — `SearchMultiSelect` в зоне пользователя (`GET /api/tasker/meetings/options`).
- **Поля**: название, повестка, первая встреча (дата), время (МСК), длительность (30 мин по умолчанию), повтор, дата
  окончания (необязательно), место/ссылка.
- **Повтор**: по будням · еженедельно по дням · раз в 2 недели (чётность — от недели первой встречи) · ежемесячно
  числом (1–28) · ежемесячно n-м днём недели (1–4 или последний).
- **Видимость**: админ — все; иначе создатель, организатор и те, у кого в зоне есть участник (руководители
  участников); менеджер — собрания, где участвует.
- **Монолитика**: миграция **278** (`tasker_meetings` — серия одной строкой, `tasker_meeting_exceptions` — отменённые
  встречи). Вхождения разворачиваются на лету (`features/tasker/meetings/engine/recurrence.ts`). Вкладка
  «Собрания» (`/tasker/meetings`: список серий, Drawer создания/правки, ближайшие 8 встреч с «Отменить/Вернуть»,
  «Отменить серию»); встречи — карточкой «Собрание» (иконка повтора) в «Неделе» и «Сегодня»
  (`GET /api/tasker/tasks` → `meetings` при заданном окне).
- **Битрикс**: одно повторяющееся событие `calendar.event.add` (rrule) в календаре организатора, раздел через
  `calendar.section.get`, `is_meeting=Y`, host = организатор, участники — attendees; правка серии = `update`,
  отмена серии = `delete`. Состояние синка — на строке (pending/synced/failed), повтор — фоновая задача `tasker`
  (раз в 5 мин, < 20 попыток) и кнопка «Повторить сейчас». Идемпотентность — поиск события по маркеру
  «Задачник · собрание #N» перед созданием.
- **Ограничения REST (проверено на портале 23.11)**: EXDATE не принимается ни в каком написании → отмена одной
  встречи только в Монолитике (в календаре участников она останется — это написано в карточке); «n-й день недели
  месяца» (BYDAY `2MO`, BYSETPOS) отбрасывается → для такого повтора событие «скользящее»: стоит на ближайшую
  неотменённую встречу и переносится фоновой задачей после неё (отмены учитывает).
- Автор события в Битриксе — владелец вебхука (2098), организатор (host) — выбранный человек; как у сессий РОПа.
- API: `GET/POST /api/tasker/meetings`, `GET/PATCH/DELETE/POST(повтор синка) /api/tasker/meetings/:id`,
  `POST /api/tasker/meetings/:id/occurrences {date, cancelled}`, `GET /api/tasker/meetings/options`. Типы — `types.ts`.

## Расписание: проверка занятости (наложение времени) — 23.11

Предупреждение, **не запрет**: при планировании форма показывает «В это время заняты 3 из 8: Иванов — Планёрка
10:00–10:30, …» и раскрываемый список «Кто и чем занят»; сохранить можно всё равно.
- Где: создание/правка собрания (ближайшие 4 встречи серии × организатор, люди, отделы целиком), создание/правка
  обучения (тренер + записанные), запись менеджера на обучение, слот сессии в форме задачи (менеджеры + постановщик;
  выбранная существующая сессия — её время). Запрос — с задержкой 600 мс после правки.
- Источники: календарь Битрикса (`calendar.accessibility.get`, одним вызовом на ≤ 50 человек, кэш 150 с; «free» не
  считается, «весь день»/«отсутствует» — считается) + события Монолитики (сессии РОПа, обучения, вхождения собраний без
  отменённых, слоты задач вне сессий).
- Копии событий, которые Монолитика сама поставила в Битрикс, отбрасываются по точному совпадению интервала с событием
  Монолитики того же человека. Свои события при правке (`exclude`: собрание / обучение / сессия / задача) не
  конфликтуют сами с собой — ни в Монолитике, ни их копии в Битриксе.
- Битрикс не ответил — показываем только Монолитику и пометку «календарь Битрикса не проверен».
- Названия событий видны только по людям в зоне пользователя (и по себе); остальные — «Занят в календаре» / тип события.
- API: `POST /api/tasker/availability {bitrixIds[], departmentIds[], includeSelf, slots[{start,end}], exclude}` →
  `{ busy[{id,name,conflicts[]}], checkedCount, bitrixChecked }`. Право — `action.tasker.assign` или
  `action.tasker.trainings.manage`. Модуль — `features/tasker/engine/availability.ts`, UI — `ui/shared/AvailabilityWarning.tsx`.
