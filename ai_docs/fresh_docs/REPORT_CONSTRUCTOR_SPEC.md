# «Мой отчёт» — конструктор отчётов в BB-коде

Спека составлена 06.08.2026 по ТЗ владельца. Источник данных согласован:
**локальная БД**, не Битрикс (месячный выгруз портала — десятки мегабайт, дёргать
его на каждое открытие раздела нельзя). Расхождения с ботовским отчётом возможны
в пределах отставания синка — обычно минуты.

## Что просил владелец (дословная суть)

> Любой отчёт строится по шаблону и принципу: менеджер отчитывается сам за себя
> со своими показателями (в конструкторе их должно быть можно добавлять как
> метрики), РОПы — за подконтрольные отделы, директора — за департаменты.
> Конструктор: выбрал дату (по умолчанию сегодня) → выбрал сущность (личный или
> отдел/департамент/филиал тем же пикером, что в отчётах) → добавил нужные
> метрики → если надо, добавил ещё сущность (метрики копируются автоматически).
> В конце в любом отчёте кроме личного — агрегированные метрики (ОС + НЦ, если
> в основном отчёте выбраны они). Всё в режиме предпросмотра с BB-кодом и кнопка
> «Копировать».

## Три существующих формата — что из них берём

### 1. «МОСКВА» (`lib/jobs/dailyMoscowReport.ts`) — эталон структуры
```
[b]Отчет МОСКВА[/b]        ← заголовок
[i]за 05.08.2026[/i]        ← дата

[b]% ПЛАНА (ДЕНЬ) — 133%[/b]  ← МЕТРИКА-ЗАГОЛОВОК с итогом по всем сущностям
Общестрой — 82%               ← и разбивка по каждой сущности
Нулевой — 204%
ЖБИ — 161%
… (неделя, месяц теми же тройками)
————                          ← разделитель между смысловыми группами
[b]Конверсия в бронь (месяц) — 27,7%[/b] + разбивка
… (в продажу, ППП, % повторных)
————
[b]ОБЩЕСТРОЙ[/b]              ← БЛОК ПО СУЩНОСТИ: все метрики одной сущности
План продаж — 11,3 млн
Сумма продаж — 9,9 млн
% выполнения — 87%
…
————
[b]ИТОГО (ОС+НЦ+ЖБИ)[/b]     ← АГРЕГАТ в конце
```
Ключевые наблюдения: (а) один и тот же набор метрик показан ДВАЖДЫ — сначала
«по метрике с разбивкой по сущностям», потом «по сущности со всеми метриками»;
(б) агрегат в конце перечисляет состав в заголовке; (в) разделитель `————`.

### 2. «КОВАЛЕНКО» (`lib/jobs/dailyGroupReport.ts`) — тот же шаблон, другие сущности
Доказательство, что формат уже обобщён: те же блоки, но сущности — команды
Общестроя (Осипов, Уханова, Руденко, Подчаший/Спецназ, Зианбетова). Значит
конструктору нужен ровно один рендерер, а сущности — параметр.

### 3. Личный отчёт менеджера (`features/manager-card/engine/managerReportText.ts`)
```
[b]Отчет: Имя Фамилия[/b]
[i]Отдел · за 05.08.2026[/i]
[b]% ПЛАНА[/b] День/Неделя/Месяц
[b]ДЕНЬ[/b] / [b]НЕДЕЛЯ[/b] / [b]МЕСЯЦ[/b] — план/факт/%/шт/брони/звонки
[b]МЕСЯЦ · ДЕТАЛИ[/b] — первичные, повторные, % повторных, CR
```
Отличие: одна сущность (сам человек) и НЕТ агрегата — что совпадает с
требованием «агрегат везде, кроме личного».

## Модель конструктора

**Состояние отчёта** (сохраняется как шаблон, чтобы не собирать каждый раз):
```
{
  date: '2026-08-05',                  // по умолчанию сегодня
  entities: [                          // 1..N
    { kind: 'self' } |
    { kind: 'department', id, title } |   // тем же пикером, что в отчётах
    { kind: 'branch', id, title }
  ],
  metrics: ['plan_pct_day', 'plan_pct_week', …],  // общий список на ВСЕ сущности
  showAggregate: true,                 // авто: false, если entities = [self]
}
```
Правила из ТЗ:
- добавление второй сущности КОПИРУЕТ текущий набор метрик (метрики общие для
  всех сущностей — иначе агрегат несчитаем);
- агрегат показывается всегда, кроме отчёта из одной личной сущности;
- заголовок агрегата собирается из коротких имён сущностей: «ИТОГО (ОС+НЦ+ЖБИ)».

**Кто что может выбрать** (гейт — существующий `lib/org/managerAccess.ts`):
менеджер — только `self`; РОП — `self` + свои отделы; директор — свои
департаменты и филиалы; руководство/админ — всё.

**Метрики.** Берём из общего каталога (`ycAnalyticsDb`, тот же пикер, что в
отчётах и в шаблонах карточки) — тогда «добавлять показатели как метрики» не
требует кода: появилась метрика в каталоге, она доступна и здесь. Для каждой
метрики нужен формат вывода (деньги «11,3 млн» / проценты «87%» / штуки) —
это уже есть в каталоге (`data_type`, `decimal_places`).

**Рендер.** Один чистый рендерер `buildReportText(state, data): string`:
1. шапка: `[b]<название>[/b]` + `[i]за <дата>[/i]`;
2. группа «метрика → разбивка по сущностям» для метрик, помеченных как
   «сводные» (проценты плана, конверсии);
3. `————`;
4. блок на каждую сущность: `[b]НАЗВАНИЕ[/b]` + все метрики;
5. `————` + агрегат (если нужен).
Предпросмотр = моноширинный блок с этим текстом + кнопка «Копировать» (уже
есть паттерн в `buildManagerReportText` → кнопка «Копировать для отчёта»).

## Порядок реализации

1. ✅ **Движок** (сделано 06.08.2026): `features/reports-builder/engine/` —
   `format.ts` (числа/даты, единственный источник правды),
   `document.ts` (модель «секции → блоки → строки» + вёрстка `————`),
   `buildReportText.ts` (композер отчётов с разбивкой по сущностям),
   `personalReport.ts` (личный отчёт — ось разбивки период, а не сущность).
   Всё чистые функции: ни БД, ни сети, ни `new Date()` без аргумента.
   Проверка — `npm run test:reports` (`scripts/assert-report-engine.ts`):
   дифф против ДОСЛОВНЫХ КОПИЙ старых рендереров на синтетических числах,
   8 сценариев, включая нулевые планы, нулевые знаменатели, отрицательные
   суммы и границы округления. `buildManagerReportText` уже переведён на
   движок (доказательство, что формат воспроизводится в проде, а не в тесте).
2. ✅ **Данные** (сделано 06.08.2026): `POST /api/my-report` +
   `GET /api/my-report/entities` (что человек вправе выбрать).
   Отдаёт НЕ текст, а `ReportSpec` с числами — клиент сам рендерит движком,
   иначе анимации нечего докручивать (из готовой строки числа не достать).
   Считает через `fetchByManagers` + `computeTotals` (свой SQL не пишет),
   планы — `lib/reports-builder/plans.ts` (та же арифметика, что в боте).
   Гейт — `lib/org/managerAccess`, второй системы прав не заводили.
   Проверено на живых данных: за 05.08.2026 «% ПЛАНА (ДЕНЬ)» дал
   ОС 86 / НЦ 204 / ЖБИ 161 при 82 / 204 / 161 в ботовском отчёте —
   расхождение только по ОС и только из-за источника (бот берёт факт живьём
   из Битрикса, конструктор — из локальной БД, как решено в начале спеки).
3. **UI** `/profile/report`: дата → пикер сущностей → пикер метрик → предпросмотр
   → «Копировать». Сохранение шаблона — как saved_reports.
4. **Замена ботовских джоб**: когда рендерер докажет байт-в-байт совпадение,
   `dailyMoscowReport`/`dailyGroupReport` переводятся на него — три реализации
   одного формата схлопываются в одну.

## Ответы владельца (06.08) — вопросы закрыты

**1. Шаблоны сохраняются.** Причём с ПРЕДУСТАНОВЛЕННЫМИ по роли: менеджеру
открывается менеджерский шаблон, руководителю — руководский. Перестроил под
себя → сохранил как свой. Механика та же, что у сохранённых отчётов
(`saved_reports`): системные пресеты + личные копии.

**2. Период выбирается.** Формулировка владельца задаёт смысл всего раздела:
«по сути любой отчёт строится по принципу — состояние на сегодня и как идём по
плану». То есть период — это не просто фильтр дат, а ответ на два вопроса
одновременно: сколько уже есть и укладываемся ли в план на этом отрезке.

**3. Только копирование в буфер, без отправки ботом.** Дословно: «пусть, сука,
заходят и читают. Важно, чтобы читали».

**4. Пропуск анимации не предусмотрен.** Дословно: «кнопку пропустить не делаем.
Пусть думают, что отчёт так собирается. Должны читать». Сборка подаётся как
единственный способ получить отчёт, а не как заставка, которую можно перемотать.

**5. Строки собираются по словам**, не построчно целиком. Подробности и бюджет
времени — в требованиях к анимации ниже.

**6. Период устроен как в отчёте МОСКВА** (ответ 06.08 на прямой вопрос).
Блок «% ПЛАНА» ВСЕГДА показывает три окна — день, неделя, месяц: это и есть
половина «как идём по плану». Остальные метрики считаются за ОДИН выбранный
период (по умолчанию месяц с начала) — половина «состояние на сегодня».
Отвергнуты: единый период на весь отчёт (тогда ежедневный отчёт не собрать —
в нём % плана всегда за три окна сразу) и период у каждой метрики свой
(добавление метрики становится в два клика вместо одного).

## АНИМИРОВАННАЯ СБОРКА — ключевая идея владельца

> Сотрудник видит шаблон отчёта слева, нажимает «Собрать отчёт», и справа отчёт
> как бы ПЕЧАТАЕТСЯ: показатели пересчитываются на глазах (цифры бегают, буквы
> появляются). Человек невольно следит за процессом сборки — «как я слежу за
> твоими рассуждениями в чате».

Это не украшение, а решение задачи «важно, чтобы читали». Приём известен по
стриминговому выводу LLM: текст, появляющийся на глазах, дочитывают заметно
чаще, чем текст, возникший целиком, — глаз следует за фронтом появления, и
человек проходит отчёт до конца вместо того, чтобы скользнуть по нему.

Требования к реализации:
- **строки собираются ПО СЛОВАМ** (решение владельца, 06.08.2026): внутри строки
  слова появляются по одному с шагом ~20-40 мс, между строками пауза ~40-80 мс.
  Не посимвольно — 60 строк по буквам это минута ожидания. По словам средний
  отчёт (~350-400 слов) собирается за 12-18 с: достаточно медленно, чтобы глаз
  шёл за текстом, и достаточно быстро, чтобы досмотреть;
- **общий бюджет сборки ≤ 20 с**: если отчёт длиннее обычного, шаг между словами
  сжимается пропорционально, а не растёт общее время. Ждать полминуты не должен
  никто — даже без кнопки «Пропустить»;
- **цифры «докручиваются»**: перед финальным значением 200-400 мс прокрутки
  случайных цифр того же разряда (эффект счётчика), затем фиксация. Крутится
  ТОЛЬКО число, подпись метрики стоит на месте — иначе рябит;
- **проценты и деньги докручиваются от нуля вверх**, а не случайным шумом:
  для «87%» глаз должен видеть рост 0→87, это читается как «считается»;
- **разделители `————` появляются мгновенно** — они структура, а не данные;
- **кнопки «Пропустить анимацию» НЕТ** (решение владельца, 06.08.2026). Дословно:
  «пусть думают, что отчёт так собирается. Должны читать». Сборка — это и есть
  способ показа отчёта, а не заставка перед ним. Не делать ни явной кнопки, ни
  скрытого «клик по области → показать всё», ни выхода по Esc/пробелу;
- **кнопка «Копировать» активируется только после финиша** — иначе скопируется
  недособранный текст. Это же и есть единственный стимул досмотреть: текст нужен
  человеку целиком, чтобы отправить его дальше;
- `prefers-reduced-motion` → отчёт появляется сразу целиком, без анимации. Это
  НЕ обход правила выше: системная настройка доступности (вестибулярные
  расстройства, укачивание от движения), а не кнопка «мне лень смотреть». Её
  включают один раз на всю ОС, а не ради пропуска конкретного отчёта;
- анимация — ЧИСТО КЛИЕНТСКАЯ поверх уже полученных данных. Никаких «данные
  подтягиваются по мере печати»: сначала ответ API целиком, потом отрисовка.
  Иначе при обрыве связи получится полуотчёт, который человек скопирует.

## Порядок реализации (обновлён)

1. Движок `buildReportText(state, data)` + воспроизведение трёх эталонов.
2. `POST /api/my-report` — данные по сущностям/метрикам/периоду.
3. UI `/profile/report`: слева шаблон (дата, период, сущности, метрики),
   справа область печати + «Собрать отчёт» / «Копировать».
4. Анимация сборки (по требованиям выше).
5. Шаблоны: системные пресеты по роли + личные.
6. Перевод ботовских джоб на общий рендерер.
