# Канбан запросов логистам — спецификация (19.11.2026)

Главная сессия-оркестратор. Решения владельца — 17–19.11 (переписка в сессии «Канбан запросов логистам»).
Подсессии строят по этому документу; меняется решение — правится здесь и пишется в WORKLOG.

## Суть

Менеджеру заказчик пишет «нужен штуцер, 10 шт.», а в калькуляторе этого нет или есть цена дешевле.
Менеджер отправляет **запрос** логисту (снабженцу). Логист находит цену, срок и поставщика и отвечает
**вариантами предложения**. Менеджер принимает вариант (по кнопке переписывает товары сделки) или
возвращает на доработку.

Сейчас это задачи Битрикса в проектах «регион × товарная группа» и приложение «[MLT] Канбан логиста»:
два типа × Новые/Выполняются/Сделаны/Завершены, вкладка «Сделки» с Проданы/Забракованы, наверху 6 плиток.
Делаем своё: запрос — наша сущность, в Битриксе — дубль-задача (см. «Дублирование»).

**Только запросы на товары.** «Свои задачи», «Дебиторка», «Курьеры», «Коррекция» — НЕ переносим (владелец 19.11).

Заменяет прототип `/logist-kanban` на заявках 1С (`sd`): адрес, пункт меню, право `section.logist_kanban`
и роль «Логист» остаются, движок на `sd` и таблица `logist_kanban_cards` (миграция 261) уходят.

## Типы запроса и откуда он берётся

| Тип | Стадия сделки (все 4 воронки, id из `features/reports/engine/stageSnapshot.ts`) |
|---|---|
| `supply` — «Запрос снабженцу» | «Сделал запрос снабженцу…»: `EXECUTING`, `C1:EXECUTING`, `C2:PREPARATION`, `C3:PREPARATION` |
| `cheaper` — «Есть цена дешевле» | «Есть цена дешевле…»: `UC_PU4HM2`, `C1:11`, `C2:4`, `C3:4` |

Входы:
1. **Робот Битрикса** на этих стадиях (исходящий вебхук → наш `/api/logist-requests/trigger`, секрет в URL,
   как `eventsAuth`, fail-closed). Создаётся **черновик** с товарами сделки (`crm.deal.productrows.get`),
   менеджеру — ссылка на форму (бот «Аналитик» + плашка в канбане/ЛК). Робот ставит админ портала (владелец).
2. **Кнопка «Запрос логисту»** в нашем приложении (карточка сделки, канбан больших чеков, «Мои запросы») —
   по одной сделке бывает несколько запросов.
3. Повторная смена стадии при открытом запросе того же типа — новый черновик НЕ создаётся.

## Форма менеджера

- Шапка из сделки, правится: населённый пункт / адрес, для каких целей, форма оплаты, дата поставки,
  комментарий, файлы.
- Позиции: товары сделки (наименование, кол-во, ед., наша цена, сумма) + **свободные позиции**
  (то, чего нет в 1С: название, кол-во, ед., комментарий, фото). Подсказка из каталога при вводе — не обязательна.
- Для `cheaper` — цена конкурента по позиции (или общая) и чья цена; обязательно.
- Очередь (см. ниже) — подставляется сама, менеджер может сменить.
- «Отправить» → запрос уходит в очередь, создаётся дубль-задача.

## Очереди (маршрутизация)

Очередь = проект Битрикса (`group_id`) «регион × товарная группа» (пример: «мск_Газобетон, кирпич и прочие
стеновые»). Справочник проектов и регионов — как у Панели снабжения (`lib/supplyPanel`, таблица `projects`,
`refs/departments.json`: ОС/НЦ). Своя таблица `logist_queues` (group_id, название, регион, департамент,
товарные группы, активна) + участники `logist_queue_members` (логисты). Очередь по умолчанию — регион
менеджера × товарная группа первой позиции. Запрос видят все логисты очереди, берёт один («Взять»).

## Жизненный цикл

`draft` → `new` (в очереди) → `in_work` (взят логистом) → `answered` (ждёт контроля менеджера)
→ `accepted` (принят) | возврат → снова `in_work` (новый цикл) ; `cancelled` (отменён менеджером).
Исход сделки (`sold` / `lost`) — из `sa.deals`, отметка на карточке и вкладка «Сделки», как сейчас.

Циклы считаются по методике Панели снабжения (`lib/supplyPanel/calc.ts`): цикл 1 — от отправки до первого
ответа, цикл N — от N-го возврата до следующего ответа; рабочее время 9–18 МСК без праздников.
Журнал событий append-only (`logist_request_events`) — источник всех метрик.

## Ответ логиста — варианты

Вариант = поставщик/база, форма оплаты, строки (позиция запроса или новая → наименование, объём, ед., цена,
сумма), доставка (машины × цена), итог (считается), срок, комментарий, файлы. Вариантов сколько угодно
(«сейчас ещё варианты скину»). Позиция «нет / аналог» — явным признаком.

**«Принять вариант»** (кнопка менеджера, с подтверждением «перепишу товары сделки так-то») →
`crm.deal.productrows.set` от имени менеджера (`callAsUser`, фолбэк — CRM-вебхук). Сейчас этот метод в проекте
не вызывается нигде — писать впервые, с проверкой на тестовой сделке и согласия владельца на первый боевой вызов.
Позиции без товара в каталоге Битрикса — строкой с PRODUCT_NAME без PRODUCT_ID.

## Карточка запроса (как задача, только лучше)

- Шапка: тип, сделка (ссылка), заказчик, менеджер, логист, очередь, SLA / огонёк, статус, ID дубль-задачи.
- Позиции запроса (таблица «Товар / Кол-во / Наша цена / Сумма / Цена конкурента»).
- Варианты ответа (карточками, сравнение «наша / конкурент / вариант» для `cheaper`).
- **Чат** — свои таблицы (`logist_request_messages`): участники — менеджер, логист, наблюдатели; файлы;
  служебные события ленты («взял», «ответил», «вернул») — из журнала. Существующий `deal-chats` — двусторонний
  РОП↔менеджер через бота, не годится как есть; берём паттерн хранения и UI.
- Действия: логист — взять / отпустить / ответить вариантом / передать в другую очередь; менеджер — принять
  вариант / вернуть с комментарием / отменить / добавить позиции; РОП/руководитель логистики — переназначить.

## Доска и фильтры (по аналогии с канбаном повторных и больших чеков)

Виды: **Доска** (колонки по статусу: Новые / В работе / Ждут контроля / Приняты; тип — чипом/цветом, не
удвоением колонок) и **Сделки** (Проданы / Забракованы). Фильтры — в URL (`useUrlState`), панель «Фильтры»
как `BigFiltersPanel` / `FiltersButton`:
- Тип запроса; Очередь (проекты, мульти); Регион; Департамент (ОС/НЦ); Товарная группа;
- Менеджер / Отдел (`DepartmentPicker`); Логист; «Только мои»; «Не взятые»;
- Статус; SLA: горит / просрочен; Возвращённые; Сумма от–до; Период создания; Исход сделки;
- Поиск (ID запроса, сделка, заказчик, товар); Сортировка: приоритет (по умолчанию) / сумма / ожидание / создан.
Все `<select>` — только `SearchSelect`/`SearchMultiSelect`.

## Приоритет («огонёк»)

Число, по нему сортируется колонка; на карточке — «почему горячий» (2–3 причины).
Факторы (веса — в настройках, админ): остаток SLA в рабочих часах (просрочен — наверх), сумма сделки,
дата поставки близко, сколько ждёт с последнего события, возвраты (каждый +), тип `cheaper` (заказчик уже
с ценой конкурента на руках). SLA по умолчанию — 3 рабочих часа на цикл (как «крайний срок» задачи сейчас),
настраивается на очередь.

## Плитки (как сейчас) и аналитика

Новые, возобновлённые, скорость взятия, скорость ответа, скорость выполнения, сумма продаж — за период,
с учётом фильтров. Руководителям — разрез регион → департамент → очередь → логист (как в Панели снабжения).

## Кто что видит

- Логист — очереди, где он участник, + свои взятые. Менеджер — свои запросы («Мои запросы» в ЛК).
- РОП — запросы менеджеров своей зоны (`ropScope`). Руководитель логистики / админ — всё.
- Право раздела `section.logist_kanban` (есть), настройки очередей и весов — `canManageLogistKanban` (новое).

## Дублирование в Битрикс (решение владельца: дублируем)

- При отправке — `tasks.task.add` в проект очереди: заголовок «Товар | кол-во | адрес», описание = шапка +
  таблица позиций, `UF_CRM_TASK = D_<deal>`, постановщик — менеджер, исполнитель — логист (при взятии).
- Статусы и ответы пишем в задачу в одну сторону: взял → «Выполняется», ответ → комментарий от имени логиста
  + «Ждёт контроля», принят → завершить, возврат → возобновить. Сообщения чата → комментарии от имени автора.
- Зачем: Панель снабжения, «Реализация», отчёты по задачам и привычки людей не ломаются на переходе.
- Обратно из Битрикса (логист ответил в задаче) — НЕ синхронизируем в первой версии; работают в Монолитике.
- **При запуске выключить существующий бизнес-процесс, создающий задачи на этих стадиях**, иначе задач две.
  Делает владелец/админ портала, в день переключения.

## Уведомления (бот «Аналитик», новый канал `logist_requests`)

Логистам очереди — новый запрос (горящий — повторно); менеджеру — ответ / вопрос в чате; логисту — возврат,
сообщение; РОПу — просрочка SLA. Менеджерам — через `sendManagerBotMessage` (dry-run).
Канбан больших чеков: «по связанной задаче пришёл ответ» (его бэклог) — берётся из нашего журнала.

## Режимы и вёрстка

Все четыре режима (`useAppMode`): десктоп, мобильный, PWA, iframe Битрикса (вход `/bx/logist-kanban`).
375/768 px, модалки — `components/ui/Modal`, таблицы в `.scroll-x`, лента вкладок — правило 12.
Встроенная инструкция «Как работать?» в формате `guide/types.ts` — с первой выкатки.

## Технически

- Миграции с 267 (system DB): `logist_queues`, `logist_queue_members`, `logist_requests`, `logist_request_items`,
  `logist_request_offers` + `_offer_lines`, `logist_request_messages`, `logist_request_events`,
  `logist_request_settings`. GRANT роли приложения (см. 257/261). `logist_kanban_cards` — дроп отдельной миграцией после выкатки.
- Код: `features/logist-kanban/{engine,ui,guide}`, API `app/api/logist-kanban/*`, триггер `app/api/logist-requests/trigger`.
- Битрикс: `bx()` из `lib/bitrix/notify.ts`, `writeOnce()` для создания (без ретраев), `callAsUser()` для действий
  от имени сотрудника. Вызывать Битрикс как можно реже: доска читает только нашу БД.

## Открытые вопросы (к владельцу, не блокируют S1)

1. Робот на стадиях: кто ставит в 4 воронках и когда выключаем старый бизнес-процесс.

3. Справочник очередей: состав логистов по проектам — берём из участников проектов Битрикса или ведём руками.
4. Веса приоритета и SLA по умолчанию — подтвердить после первых недель.
