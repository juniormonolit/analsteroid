# Канбан запросов логистам — спецификация (19.11.2026)

Главная сессия-оркестратор. Решения владельца — 17–19.11 (переписка в сессии «Канбан запросов логистам»).
Подсессии строят по этому документу; меняется решение — правится здесь и пишется в WORKLOG.

## Суть

Менеджеру заказчик пишет «нужен штуцер, 10 шт.», а в калькуляторе этого нет или есть цена дешевле.
Менеджер отправляет **запрос** логисту (снабженцу). Логист находит цену, срок и поставщика и отвечает
**вариантами предложения**. Менеджер принимает вариант (по кнопке переписывает товары сделки) или
возвращает на доработку.

Сейчас это задачи Битрикса в проектах «регион × товарная группа» и приложение «[MLT] Канбан логиста»:
два типа × Новые/Выполняются/Сделаны/Завершены, вкладка «Сделки» с Проданы/Забракованы, наверху 6 плиток.
Делаем своё: запрос — наша сущность, в Битриксе — дубль-задача (см. «Дублирование»).

**Только запросы на товары.** «Свои задачи», «Дебиторка», «Курьеры», «Коррекция» — НЕ переносим (владелец 19.11).

Заменяет прототип `/logist-kanban` на заявках 1С (`sd`): адрес, пункт меню, право `section.logist_kanban`
и роль «Логист» остаются, движок на `sd` и таблица `logist_kanban_cards` (миграция 261) уходят.

## Типы запроса и откуда он берётся

| Тип | Стадия сделки (все 4 воронки, id из `features/reports/engine/stageSnapshot.ts`) |
|---|---|
| `supply` — «Запрос снабженцу» | «Сделал запрос снабженцу…»: `EXECUTING`, `C1:EXECUTING`, `C2:PREPARATION`, `C3:PREPARATION` |
| `cheaper` — «Есть цена дешевле» | «Есть цена дешевле…»: `UC_PU4HM2`, `C1:11`, `C2:4`, `C3:4` |

Входы:
1. **Робот Битрикса** на этих стадиях (исходящий вебхук → наш `/api/logist-requests/trigger`, секрет в URL,
   как `eventsAuth`, fail-closed). Создаётся запрос с товарами сделки (`crm.deal.productrows.get`); режим —
   настройка `robotMode` (S2): **`send` (по умолчанию) — сразу в «Новые»**, как бизнес-процесс сейчас (не прошли
   проверки отправки — у `cheaper` нет цены конкурента, в сделке нет товаров, нет очереди — остаётся черновиком);
   `draft` — всегда черновик. Менеджеру — ссылка бота «Аналитик» на форму `/logist-requests/<id>` («дополнить
   запрос» / «заполнить и отправить»). Робот ставит админ портала (владелец) — инструкция ниже.
2. **Кнопка «Запрос логисту»** в нашем приложении (карточка сделки, канбан больших чеков, «Мои запросы») —
   по одной сделке бывает несколько запросов.
3. Повторная смена стадии при открытом запросе того же типа — новый черновик НЕ создаётся.

## Форма менеджера

- Шапка из сделки, правится: населённый пункт / адрес, для каких целей, форма оплаты, дата поставки,
  комментарий, файлы.
- Позиции: товары сделки (наименование, кол-во, ед., наша цена, сумма) + **свободные позиции**
  (то, чего нет в 1С: название, кол-во, ед., комментарий, фото). Подсказка из каталога при вводе — не обязательна.
- Для `cheaper` — цена конкурента по позиции (или общая) и чья цена; обязательно.
- Очередь (см. ниже) — подставляется сама, менеджер может сменить.
- «Отправить» → запрос уходит в очередь, создаётся дубль-задача.

## Очереди (маршрутизация)

Очередь = проект Битрикса (`group_id`) «регион × товарная группа» (пример: «мск_Газобетон, кирпич и прочие
стеновые»). Справочник проектов и регионов — как у Панели снабжения (`lib/supplyPanel`, таблица `projects`,
`refs/departments.json`: ОС/НЦ). Своя таблица `logist_queues` (group_id, название, регион, департамент,
товарные группы, активна) + участники `logist_queue_members` (логисты). **Состав очереди = участники проекта
Битрикса** (решение владельца 19.11: «так понятно, кто за какую группу товаров отвечает»): синк `sonet_group.user.get`
раз в 6 ч (фоновая задача `logistQueueMembers`) + кнопка «обновить»; ручных правок нет, источник правды — Битрикс. Очередь по умолчанию — регион
менеджера × товарная группа первой позиции. Запрос видят все логисты очереди, берёт один («Взять»).

## Жизненный цикл

`draft` → `new` (в очереди) → `in_work` (взят логистом) → `answered` (ждёт контроля менеджера)
→ `accepted` (принят) | возврат → снова `in_work` (новый цикл) ; `cancelled` (отменён менеджером).
Исход сделки (`sold` / `lost`) — из `sa.deals`, отметка на карточке и вкладка «Сделки», как сейчас.

Циклы считаются по методике Панели снабжения (`lib/supplyPanel/calc.ts`): цикл 1 — от отправки до первого
ответа, цикл N — от N-го возврата до следующего ответа; рабочее время 9–18 МСК без праздников.
Журнал событий append-only (`logist_request_events`) — источник всех метрик.

## Ответ логиста — варианты

Вариант = поставщик/база, форма оплаты, строки (позиция запроса или новая → наименование, объём, ед., цена,
сумма), доставка (машины × цена), итог (считается), срок, комментарий, файлы. Вариантов сколько угодно
(«сейчас ещё варианты скину»). Позиция «нет / аналог» — явным признаком.

**«Принять вариант»** (кнопка менеджера, с подтверждением «перепишу товары сделки так-то») →
`crm.deal.productrows.set` от имени менеджера (`callAsUser`, фолбэк — CRM-вебхук). Сейчас этот метод в проекте
не вызывается нигде — писать впервые, с проверкой на тестовой сделке и согласия владельца на первый боевой вызов.
Позиции без товара в каталоге Битрикса — строкой с PRODUCT_NAME без PRODUCT_ID.

## Карточка запроса (как задача, только лучше)

- Шапка: тип, сделка (ссылка), заказчик, менеджер, логист, очередь, SLA / огонёк, статус, ID дубль-задачи.
- Позиции запроса (таблица «Товар / Кол-во / Наша цена / Сумма / Цена конкурента»).
- Варианты ответа (карточками, сравнение «наша / конкурент / вариант» для `cheaper`).
- **Чат** — свои таблицы (`logist_request_messages`): участники — менеджер, логист, наблюдатели; файлы;
  служебные события ленты («взял», «ответил», «вернул») — из журнала. Существующий `deal-chats` — двусторонний
  РОП↔менеджер через бота, не годится как есть; берём паттерн хранения и UI.
- Действия: логист — взять / отпустить / ответить вариантом / передать в другую очередь; менеджер — принять
  вариант / вернуть с комментарием / отменить / добавить позиции; РОП/руководитель логистики — переназначить.

## Доска и фильтры (по аналогии с канбаном повторных и больших чеков)

Виды: **Доска** (колонки по статусу: Новые / В работе / Ждут контроля / Приняты; тип — чипом/цветом, не
удвоением колонок) и **Сделки** (Проданы / Забракованы). Фильтры — в URL (`useUrlState`), панель «Фильтры»
как `BigFiltersPanel` / `FiltersButton`:
- Тип запроса; Очередь (проекты, мульти); Регион; Департамент (ОС/НЦ); Товарная группа;
- Менеджер / Отдел (`DepartmentPicker`); Логист; «Только мои»; «Не взятые»;
- Статус; SLA: горит / просрочен; Возвращённые; Сумма от–до; Период создания; Исход сделки;
- Поиск (ID запроса, сделка, заказчик, товар); Сортировка: приоритет (по умолчанию) / сумма / ожидание / создан.
Все `<select>` — только `SearchSelect`/`SearchMultiSelect`.

## Приоритет («огонёк»)

Число, по нему сортируется колонка; на карточке — «почему горячий» (2–3 причины).
Факторы (веса — в настройках, админ): остаток SLA в рабочих часах (просрочен — наверх), сумма сделки,
дата поставки близко, сколько ждёт с последнего события, возвраты (каждый +), тип `cheaper` (заказчик уже
с ценой конкурента на руках). SLA по умолчанию — 3 рабочих часа на цикл (как «крайний срок» задачи сейчас),
настраивается на очередь.

## Плитки (как сейчас) и аналитика

Новые, возобновлённые, скорость взятия, скорость ответа, скорость выполнения, сумма продаж — за период,
с учётом фильтров. Руководителям — разрез регион → департамент → очередь → логист (как в Панели снабжения).

## Кто что видит

- Логист — очереди, где он участник, + свои взятые. Менеджер — свои запросы («Мои запросы» в ЛК).
- РОП — запросы менеджеров своей зоны (`ropScope`). Руководитель логистики / админ — всё.
- Право раздела `section.logist_kanban` (есть), настройки очередей и весов — `canManageLogistKanban` (новое).

## Дублирование в Битрикс (решение владельца: дублируем)

- При отправке — `tasks.task.add` в проект очереди: заголовок «Товар | кол-во | адрес», описание = шапка +
  таблица позиций, `UF_CRM_TASK = D_<deal>`, постановщик — менеджер, исполнитель — логист (при взятии).
- Статусы и ответы пишем в задачу в одну сторону: взял → «Выполняется», ответ → комментарий от имени логиста
  + «Ждёт контроля», принят → завершить, возврат → возобновить. Сообщения чата → комментарии от имени автора.
- Зачем: Панель снабжения, «Реализация», отчёты по задачам и привычки людей не ломаются на переходе.
- Обратно из Битрикса (логист ответил в задаче) — НЕ синхронизируем в первой версии; работают в Монолитике.
- **При запуске выключить существующий бизнес-процесс, создающий задачи на этих стадиях**, иначе задач две.
  Делает владелец/админ портала, в день переключения.
- **Реализация (S4, 19.11)** — `features/logist-kanban/engine/bitrix/` (подробно — шапка `sync.ts`, `dealRows.ts`):
  очередь `logist_bx_outbox` (миграция 270), шаги по порядку, сбой → `bx_sync_status='error'`/`bx_sync_error`, повтор —
  фоновая `logistBxSync` и `POST /api/logist-kanban/request/:id/bx-sync` → `{ done, error }`. Флаги (по умолчанию выкл.):
  `LOGIST_BX_WRITE`, `LOGIST_BX_DEAL_ROWS`, `LOGIST_BX_ONLY_GROUPS`, `LOGIST_BX_ONLY_DEALS`. Исполнитель задачи до взятия —
  менеджер (Битрикс требует исполнителя). Отправлен при выключенной записи — задачи не будет и позже.
- **«Принять вариант» для UI (S3):** перед кнопкой — `GET /api/logist-kanban/request/:id/deal-rows?offerId=` →
  `DealRowsPreview` (`engine/bitrix/types.ts`: before/after/changes/warnings/hash, `writeEnabled`), подтверждение →
  action `accept` с `dealRows: { confirm: true, hash }`. Без `dealRows` принять можно, товары не меняются (`skipped`).
  Ошибка записи — `dealRowsStatus='error'` + `dealRowsError`, повтор — `POST …/deal-rows { confirm: true, hash }`.

## Уведомления (бот «Аналитик», новый канал `logist_requests`)

Логистам очереди — новый запрос (горящий — повторно); менеджеру — ответ / вопрос в чате; логисту — возврат,
сообщение; РОПу — просрочка SLA. Менеджерам — через `sendManagerBotMessage` (dry-run).
Канбан больших чеков: «по связанной задаче пришёл ответ» (его бэклог) — берётся из нашего журнала.

Все четыре режима (`useAppMode`): десктоп, мобильный, PWA, iframe Битрикса (вход `/bx/logist-kanban`).

## API (S1, 19.11 — контракт для S2–S5)

**Контракт типов — `features/logist-kanban/engine/requests/contract.ts`** (без рантайм-импортов, тянуть можно и в
клиент). Поля только добавляются; переименование — правкой спеки и всех потребителей в одном коммите.
Даты — ISO UTC, календарные — `YYYY-MM-DD`; люди — bitrix id. Ошибка любого эндпоинта — `{ error, code? }`,
`code`: `forbidden` (403) / `not_found` (404) / `conflict` (409, устарела `version`) / `transition` (409, действие
недоступно в статусе) / `invalid` (400).

| Метод и путь | Тело → ответ | Кто |
|---|---|---|
| `GET /api/logist-kanban/board?view=board\|deals&<фильтры>&limit=100` | → `BoardResponse` (колонки, свои черновики, плитки, варианты фильтров, `me`) | все вошедшие; данные режутся видимостью |
| `POST /api/logist-kanban/drafts` | `CreateDraftBody` → `CreateDraftResponse` (201 создан / 200 уже был); `send: true` — без черновика, сразу `new` | менеджер; от чужого имени — `canManage` |
| `GET /api/logist-kanban/request/:id[?peek=1]` | → `RequestDetails` (позиции, варианты, чат, журнал, циклы, `can`, `roles`); без `peek` — чат прочитан | кто видит |
| `PATCH /api/logist-kanban/request/:id` | `UpdateDraftBody` → `RequestDetails` (= `update_draft`) | автор черновика |
| `POST /api/logist-kanban/request/:id/action` | `ActionBody` → `ActionResponse` | по `can` |
| `GET /api/logist-kanban/request/:id/messages?after=<id>` | → `MessagesResponse` (новые сообщения + лента событий) | кто видит |
| `POST /api/logist-kanban/request/:id/messages` | `PostMessageBody` → `PostMessageResponse` (201) | кто видит |
| `GET /api/logist-kanban/deal/:dealId` | → `DealRequestsResponse` (запросы по сделке, открытый по типу) | кто видит |
| `GET /api/logist-kanban/queues` | → `QueuesResponse` (очереди, настройки, `canManage`) | все вошедшие |
| `PUT /api/logist-kanban/queues` | `QueueUpsertBody` → `{ queue }` (без состава — он только из Битрикса) | `canManage` |
| `POST /api/logist-kanban/queues/seed` | → `SeedQueuesResponse` — посев очередей из снимка Панели снабжения | `canManage` |
| `POST /api/logist-kanban/queues/sync-members` | → `SyncMembersResponse` — состав из участников проектов Битрикса (кнопка «обновить») | `canManage` |
| `GET` / `PUT /api/logist-kanban/settings` | `SettingsBody` (частично) → `LogistSettings` | чтение — все; запись — `canManage` |
| `POST`/`GET /api/logist-requests/trigger?key=…&deal=…` | → `TriggerResponse` (S2) — робот стадии | секрет `LOGIST_TRIGGER_SECRET` |
| `GET /api/logist-requests/deal/:dealId` | → `DealSnapshotResponse` (S2) — шапка/товары сделки для формы, очередь по умолчанию, открытые | все вошедшие |

Действия (`ActionBody.action`), допустимые статусы → новый статус, кто (админ = `canManage` — всё допустимое):

| action | из | в | кто |
|---|---|---|---|
| `update_draft` (шапка + позиции полной заменой) | draft | — | менеджер-автор |
| `send` (проверки: очередь, ≥1 позиция, у `cheaper` цена конкурента по позиции или общая) | draft | new | менеджер |
| `take` | new | in_work | логист очереди |
| `release` | in_work | new | держатель, руководитель очереди |
| `transfer {queueId}` | new, in_work | new (держатель снят) | держатель, логист очереди (не взятый), руководитель очереди |
| `reassign {logistBitrixId}` | new, in_work, answered | in_work (answered — без смены) | руководитель очереди, РОП зоны |
| `answer {offer}` (ещё варианты — можно повторно) | new, in_work, answered | answered | держатель; из «Новых» — логист очереди (становится держателем) |
| `withdraw_offer {offerId}` | in_work, answered | — | держатель |
| `return {comment}` (новый цикл; без держателя → new) | answered | in_work | менеджер |
| `accept {offerId}` → хук записи товаров сделки (S4) | answered | accepted | менеджер |
| `cancel {reason?}` | draft, new, in_work, answered | cancelled | менеджер, РОП зоны |
| `add_items {items}` | draft…answered | — | менеджер |

Видимость (`status.ts canSee`, в SQL — `repo.ts visibilitySql`): черновик — автору и `canManage`; остальное — менеджеру
запроса, держателю, участникам очереди, РОПу зоны (`ropScope` → менеджеры), `canManage` — всё.
`canManageLogistKanban` = супер-админ / роль «Администратор» / пофамильное право `action.logist_kanban.manage`.
Разделу-странице по-прежнему нужен `section.logist_kanban` (это решает S3); API открыт всем вошедшим, потому что
менеджеры создают и смотрят свои запросы без этого права.

Фильтры доски — `LogistFilters`, списки повторяющимися ключами (`?type=supply&queue=5&queue=7`, в названиях групп
запятые). Разбор/сборка — `parseFilters` / `filtersToSearchParams` (`engine/requests/filters.ts`, клиентобезопасен).
Сортировка `?sort=priority|sum|waiting|created`. Закрытые без периода — за 45 дней. Плитки — за `from..to` или 30 дней.

Точки расширения (`engine/requests/hooks.ts`, вызываются после коммита, ошибка не откатывает действие):
`afterLogistChange(ctx)` — S4 (дубль-задача, статусы, комментарии) и S5 (уведомления);
`writeDealRowsForAcceptedOffer(...)` — S4, сейчас заглушка → `deal_rows_status='skipped'`.

## Робот на стадиях — инструкция админу портала (S2)

**Один раз на сервере.** Сгенерировать секрет (`openssl rand -hex 24`), положить в `secrets.env` прода строкой
`LOGIST_TRIGGER_SECRET=<секрет>` и перезапустить (`sudo systemctl restart monolitika`). Пока секрета нет, триггер
отвечает 503 всем (fail-closed) — запросы не создаются, в `app.log` строка «LOGIST_TRIGGER_SECRET не задан».

**URL робота** (одинаковый для всех 8 стадий; тип запроса сервер определяет сам по текущей стадии сделки):

```
https://monolitika.mlt-it.ru/api/logist-requests/trigger?key=<секрет>&deal={{ID}}
```

`{{ID}}` — не набирать руками: в поле URL кнопкой «…» → «Поля сделки» → «ID» (в URL окажется `{=Document:ID}` —
это то же самое). Можно добавить подсказку `&type=supply` / `&type=cheaper` — сработает, только если сделка успела
уйти со стадии, пока шёл вебхук.

**Где ставить** (CRM → Сделки → воронка → «Роботы» / «Автоматизация»), робот «Исходящий вебхук»
(раздел «Другое»), «Выполнить: сразу», условие — без условий:

| Воронка | «Сделал запрос снабженцу…» | «Есть цена дешевле…» |
|---|---|---|
| Общая (0) | `EXECUTING` | `UC_PU4HM2` |
| C1 | `C1:EXECUTING` | `C1:11` |
| C2 | `C2:PREPARATION` | `C2:4` |
| C3 | `C3:PREPARATION` | `C3:4` |

Итого 8 роботов. Проверка после установки: перевести тестовую сделку на стадию → в `app.log` строка
`[logist-requests/trigger] сделка N: created №M (new)`; повторный перевод на ту же стадию → `exists` (второй запрос не
создаётся, пока первый открыт). Ручная проверка без робота — открыть URL в браузере с реальным id сделки (GET работает
так же).

**В день переключения** — выключить старый бизнес-процесс, создающий задачи на этих стадиях (иначе задач две), и
включить функцию бота «Запросы логистам: менеджеру» (Настройки → Боты → Аналитик; миграция 271). Пока включён общий
dry-run менеджерских пушей, сообщения только пишутся в журнал бота.

**Режим робота** — `PUT /api/logist-kanban/settings {"robotMode":"draft"}` (руководитель логистики/админ) переключает
на «сначала форма»; `"send"` — обратно. Экран настройки — у S3 (настройки очередей и весов).
