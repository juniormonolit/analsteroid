Источник требований: ТЗ №1 «Движок диагностики» и ТЗ №2 «Конструктор сценариев v2»
(владелец, 10.09.2026, файлы в его Downloads; исследование `kpi-tree-research`

## Решения 10.09.2026

1. **v1 и v2 живут вместе.** В конструкторе два типа триггера: «по порогу метрики» (v1,
   уже на проде) и «по диагнозу» (v2). Диагностику начинаем сразу, параллельно — «она сама
   будет улучшаться».
2. **Фаза 0 (проверки §12 ТЗ №1)** — через API под супер-админом, запуск из браузера:
   `/settings/diagnostics/checks` → `GET /api/diag/checks?only=…`. Результат дублируется в
   stdout прода (`[diag-checks]`, читать из `app.log`).
3. **Миграции diag_*** — номера 206+.
4. **Тиковое окно = всегда 100 последних закрытых сделок (включая зомби), тик = 10.**
   Ограничения «не старше 90 дней» НЕТ. (Отменяет N∈[40,200] и T=90 из ТЗ.)
5. **Зомби считаются проигранными только в движке диагностики.** Плюс: в основном отчёте
   нужен переключатель в настройках отчёта «учитывать зомби-сделки как проигранные» —
   отдельная задача после появления `diag_zombie_thresholds`.
6. **Атрибуция `current_manager_id` и повторность по истории клиента — только в движке.**
   Живые отчёты (`stageConversions.ts`, `funnels.is_repeat`) не трогаем.
7. **Сезонность** — по существующим данным, эталон: **август 2025 — август 2026**,
   записать как константную таблицу коэффициентов (корреляция из года в год не меняется).
8. **Порог зомби** — считать по каждой товарной группе отдельно, отсечка **P(продажа) < 5%**.
   Ожидание владельца «4–5 дней» — не факт, не подгонять.
9. **Маршрутизация (`diag_routing`)** — настраиваемый список получателей **на каждый филиал**,
   владелец заполнит руками; по умолчанию везде владелец (Bitrix ID **2098**) на время тестов.
10. **Доступ к `/diagnostics`** — новое право `section.diagnostics`, срез через `sessionScope`
    (РОП видит свой филиал, супер-админ — всё).
11. **Контрольная группа** — «надо быстрее». Решение исполнителя (см. ниже): 50/50 на этапе
    валидации ребра, потом 20% контроль для подтверждённых рёбер; порог наблюдений
    n ≥ 20 в руке. Всё в настройках.
12. **Дефолты** (`track_days`, `hold_days`, `pause_days`, `max_prior_runs_same_lever`,
    `zombie_min`, k/h/λ детекторов, control_share, …) — все настраиваемые, с подробными
    описаниями в UI настроек; стартовые значения ставит исполнитель.
13. **Тексты слотов** — исполнитель генерирует черновики (5 вариантов × 3 тона) для стартовых
    рычагов, владелец утверждает.
14. **Менеджер НЕ может отключить «Аналитика» сам.** Кнопки «Не пишите мне» не будет;
    самостоятельный opt-out (`manager_bot_prefs` через `/api/me/bot-prefs`) для сценариев
    и диагностики не действует. Отключить может только админ.
15. **Сценарии для руководителей (ТЗ №2 §8) — позже**, в BACKLOG.

## Контрольная группа — обоснование выбора 50/50 на старте

Цель — быстрее набрать статистику по рёбрам. Мощность сравнения двух долей максимальна при
равных руках: при 20% контроля нужно в ~1,6 раза больше диагнозов на то же число
наблюдений в меньшей руке. Поэтому: пока ребро в статусе `expert`/`testing` —
`control_share = 0.5`; как только ребро `confirmed` — 0.2 (помогаем большинству, контроль
только чтобы не потерять сигнал). Порог пересчёта весов — n ≥ 20 в каждой руке (вместо 30):
быстрее реагируем, цена — больше ложных подтверждений, компенсируется тем, что вес двигается
шагом 0.1 и откатывается. Все три числа — в `diag_settings`.
