# «Большой брат» — ТЗ (утверждено владельцем 25.11.2026)

Внутренний сервис Монолитики в меню «Ещё». Журнал действий пользователей + аналитика
«активность ↔ показатели». Консультация архитектуры — Fable (25.11), ответы владельца — ниже.

## Зачем

1. **Оценка РОПов (запрос Осипова) — главное.** Эффективность РОПа = как он ставит задачи
   подчинённым в Задачнике, Канбане больших чеков, Канбане повторки (количество, регулярность,
   охват подчинённых, скорость реакции, доведение до конца, эффект) — против показателей отдела.
2. **Дисциплина задач — у всех** (продажи + логисты): вовремя ли закрывает свои задачи, сколько
   просрочено, сколько висит.
3. **Сторож МОПов** — бот «Аналитик» пишет, если менеджер в работе, но долго не двигал сделки,
   не звонил и не решал задачи. Настраиваемые правила с эскалацией, как в «Контроле звонков».
4. **Активность внутри сервисов Монолитики** — кто чем пользуется, когда, с какого устройства.

## Решения владельца (25.11)

| Вопрос | Решение |
|---|---|
| PHP-разработчик на коробке Битрикса | **Нет.** Только то, что уже приходит + REST. Автора смены стадии нет → сдвиг сделки засчитывается ответственному (для МОПов приемлемо) |
| Сотрудники знают о мониторинге | Да, открытый режим |
| Чаты Битрикса | Не брать вообще |
| Дела (`crm.activity`, CRM_TODO) | Не интересны, не брать |
| Учёт рабочего дня (timeman) | Ненадёжен, не брать |
| Влияние на деньги/XP/рейтинги | Нет. В `features/xp` не подключать |
| Кого мониторим | Продажи (МОП, РОП, директора) + логисты |
| Хранение | Подробная лента — 90 дней, дневные агрегаты — бессрочно |
| Оповещения | Настраиваемые правила с эскалацией по образцу `call_control_rules` (получатель: менеджер / РОП / директор отдела / директор компании / фикс. ID; порог минут; задержка эскалации) |
| Рабочее время | Только рабочие дни по производственному календарю (`lib/metrics/productionCalendar.ts`). Окно — настройка (дефолт 9:00–18:00 МСК). Обед — 1 час, поэтому порог тишины по умолчанию 120 мин (> обед + запас); порог — настройка |
| Больничные/отпуска | Не по карточкам. Менеджер **«в работе» сегодня**, если сегодня получил новую сделку или по его сделкам была смена стадии (то же определение, что `fetchRecentlyActiveManagerIds` в `lib/jobs/managerDigest.ts`: `deal_events.manager_id` / `deals.current_manager_id` + `created_at`), либо был иной сигнал (звонок, движение задачи, действие в Монолитике). Нет ни одного сигнала за день — сторож молчит (вероятно, отсутствует) |
| Задачи РОПа, поставленные прямо в Битриксе | **Считать**, если задача в группах трёх сервисов (Задачник — группа из `tasker_settings`; большие — `BIG_DEALS_GROUP_IDS`; повторка — `REPEAT_PROJECT_GROUP_ID`). Автор — `sa.bitrix_task_current.created_by` |
| Доступ | Раздел — только уровень «директор и выше» (superadmin / Администратор / роль Директор). **Рейтинг РОПов — только админы** (superadmin / Администратор) |

## Данные

Все новые таблицы — в БД system; миграции с `GRANT` роли приложения (см. память prod-migration-needs-grants).

- **`activity_events`** — нормализованный журнал действий **в Монолитике**:
  `id bigserial, ts timestamptz, user_id uuid, login, bitrix_user_id text, role_name, surface text,
  kind text, action text, section text, entity_type text, entity_id text, deal_id bigint,
  request_id text, payload jsonb`. Индексы `(bitrix_user_id, ts)`, `(kind, ts)`. Пишется
  только через `lib/activity/log.ts::logActivity(session, {...})` — никогда не бросает (как
  `features/repeat-kanban/engine/log.ts`). Чужие пофичевые журналы (`repeat_kanban_events`,
  `logist_request_events`) **не дублируем** — читаем адаптерами.
- **`activity_minutes`** — `(bitrix_user_id, bucket timestamptz (5 мин), source, surface, section)`
  PK, `ON CONFLICT DO NOTHING`. Heartbeat Монолитики + производные сигналы.
- **`activity_daily`** — снимок на (snap_date, bitrix_user_id): активные минуты Монолитики,
  первый/последний сигнал дня по всем источникам, `in_work bool`, счётчики по kind (jsonb),
  задачи поставлено/закрыто/просрочено, отдел и РОП **на дату** из `sa.org_resolved_hierarchy`.
  Сборка — `runOnceADayMsk` ночью + пересчёт «сегодня» раз в 15 мин; ключ в `BACKGROUND_JOBS_ALLOW`.
- **Сторож:** `idle_watch_settings` (enabled, dry_run, окно часов, mirror_bitrix_user_id, курсоры),
  `idle_watch_rules` (порог минут без сигнала, получатель, задержка эскалации, шаблон, sort_order,
  is_active), `idle_watch_cases` / журнал отправок (по образцу таблиц `call_control_*`).
- TTL: `activity_events` и `activity_minutes` — чистка старше 90 дней; `activity_daily` — бессрочно.

### Таксономия `kind`
`mono_view` (раздел), `mono_action` (мутация в сервисе), `session` (login/logout), и производные
из адаптеров: `call` (out_reached / out_attempt / in), `deal_stage`, `deal_new`, `task`
(create / close / overdue / return / comment), `kanban` (повторка), `logist`.

## Аналитика

### Рейтинг РОПов (только админы)
По РОПу за период, против показателей его отдела из движка отчётов:
- задач поставлено (всего и на подчинённого), по сервисам (Задачник / большие / повторка; через
  Монолитику и напрямую в Битриксе);
- регулярность — дней с постановкой задач, провалы по неделям;
- охват — доля подчинённых, получивших хоть одну задачу;
- реакция — время от появления большого чека / клиента в очереди повторки до первой задачи;
- доведение — приняты / проверены / закрыты; для Задачника — доля задач с вердиктом «показатель вырос»;
- активность самого РОПа в Монолитике (дни, минуты, разделы).
Сопоставление — scatter «активность РОПа × показатели отдела», таблица с сортировкой.

### Дисциплина задач (все: продажи + логисты)
Закрыто вовремя / с опозданием / просрочено сейчас / висит без движения N дней / возвращено на доработку.

### Лента и календарь человека
Лента дня полосами по источникам (Монолитика / звонки / сделки / задачи / нет сигнала), календарь
по дням (закрывает пункт BACKLOG «Heatmap активности»).

### Сторож МОПов
Работает только в рабочий день по производственному календарю, внутри окна, только когда менеджер
«в работе» сегодня. Сигнал = звонок, смена стадии / новая сделка, движение задачи, действие в
Монолитике. Правила — как в «Контроле звонков»: N минут тишины → получатель; эскалация дальше по
цепочке. `dry_run` + дубль на `mirror_bitrix_user_id` на время обкатки. Лаг данных: звонки и задачи
≤ 5 мин (Roan), сделки — live (n8n).
