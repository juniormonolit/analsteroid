# Спека: клик по когорте на графиках открывает список сделок

Задача 2546. Владелец (Серёга), дословно: «сделай так, чтобы при нажатии на любую
когорту на графиках появлслся список сделок. Можно в слайдере слева, можно просто
внизу под графиками списком.»

## Проблема

В разделе «Графики» (`/charts`) три кривые — «Вероятность продажи» (пресет
`priced`), «Вероятность продажи от дней в работе (WORK)» (пресет `work`) и
«Когорта Созвонился → продажа по дням» — показывают только агрегаты (тултип по
ховеру/тапу). Раньше клик по корзине открывал что-то похожее, но 29.07 его
заменили тултипом (см. комментарий в `SurvivalChart.tsx`). Владелец хочет вернуть
интерактив: клик по любой корзине/точке → список сделок, из которых эта корзина
состоит, с учётом активных фильтров страницы (период, отдел, воронка, тип
клиента, товарные группы).

## Решение по подаче

**Боковая слайд-панель**, а не блок под графиком — переиспользует существующий
визуальный паттерн дрилл-дауна отчётов (`PanelCloseTab`, `SLIDE_BACKDROP_BG`,
`useSlideClose`, `DealsListBody`/`DealsTable` из
`features/reports/ui/DrilldownDrawer.tsx`), знаком пользователю из раздела
«Продажи» и не мнёт график под собой на мобиле.

**Что показывает клик по одной корзине.** У каждой корзины/точки два числа:
`total`/`sold` (survival) или `cohort`/`sold` (когорта). Гадать, какое из них
пользователь хочет, не нужно — панель открывается с сегментированным
переключателем **«Все N / Продано M»** (числа берутся из уже загруженных данных
графика, без лишнего запроса на подсчёт), по умолчанию выбрано «Все N» (это же
число подписано на самом бакете). Переключение на «Продано M» перезапрашивает
список с тем же фильтром, но `filter=sold`.

**Клик по чему именно.** `onClick` вешается на весь `<ComposedChart>`
(`activeLabel` из события Recharts) — работает и по бару, и по линии/точке, и
на тач-устройствах (единая область клика на всю корзину), не требует отдельных
обработчиков на `<Bar>`/`<Line>`.

## Три графика — три поведения

1. **`priced`/`work` (SurvivalChart)** — клик по бакету дней в стадии.
   Список = сделки этого бакета (тот же диапазон `days`, что использует
   агрегация). Переключатель «Все N / Продано M» = `total`/`sold` бакета.
2. **Когорта «Созвонился → продажа»** — клик по дню N. «Все N» = сделки,
   «дожившие» минимум N дней (`observedDays >= N`, at-risk на день N); «Продано
   M» = сделки, продавшие ровно на день N (`eventDay === N`). Обе трактовки
   осмысленны и обе присутствуют на графике (серый бар и линия) — переключатель,
   а не выбор одной по умолчанию.

Ни для одного из трёх графиков клик не бессмысленен — все три показывают
когорты конкретных сделок, просто с разной семантикой числа.

## Технически (реюз, не с нуля)

- **Переиспользуется**: `DealsListBody` + `DealsTable`
  (`features/reports/ui/DrilldownDrawer.tsx`) — те же колонки (`DEAL_FIELDS`),
  ссылка на сделку в Bitrix (`DealNameCell`), копирование ссылки, сортировка по
  колонкам, баннер «Итого: N сделок · Σ» с обрезкой по `LIMIT 1000`
  (уже встроено в компонент). `DealsListBody` получает необязательный
  `fetchOverride` (queryKey + fetchFn) — используется вместо `query`
  (`URLSearchParams`) там, где список выбирается явным набором `deal_id`
  (нельзя выразить через существующие `managerId`/`productGroup`/`sourceDim` —
  когорта строится по `sa.deal_events`, а не по плоскому фильтру `deals`).
  Существующие вызовы (`FlatDealsView`, `SubDealsView`) не меняются.
- **Новые роуты** (по образцу `/api/charts/stage-survival`,
  `/api/charts/called-to-sale-cohort` — тот же `permError(session,
  'section.charts')`, та же валидация периода/фильтров):
  - `POST /api/charts/stage-survival/deals` — `{preset, bucketLabel, filter,
    period, dealScope, clientType, departmentIds, productGroupMode,
    productGroupIds}` → `{deals, total_count, total_amount}`.
  - `POST /api/charts/called-to-sale-cohort/deals` — то же, `{day, filter}`
    вместо `{preset, bucketLabel}`.
  - Оба вычисляют `deal_id` тем же SQL (те же CTE `target_stages`/
    `first_entry`/`cohort`, что в `stageSurvival.ts`/`calledToSaleCohort.ts` —
    просто добавлено `deal_id` в SELECT), затем гидрируют строки той же формой,
    что `/api/reports/deals` (JOIN `stages`/`product_groups`/`funnels` +
    `loadManagerInfoMap`/`loadSourceMap`), с `LIMIT 1000` и безлимитным
    count/sum — байт-в-байт тот же паттерн, что существующий роут (не трогаем
    сам `/api/reports/deals` — он и так перегружен инцидентами #2340..#2390).
- **Число в списке = число на графике**: список берёт ТЕ ЖЕ `days`/`observedDays`
  границы бакета, что использует агрегация (общий код, не копия с дрейфом).

## Не-цели

- Не трогаем существующий дрилл-даун отчётов (`/api/reports/deals`,
  `DrilldownDrawer`) — только читаем из него компоненты.
- Не добавляем группировку/мини-отчёт внутри панели графиков — только плоский
  список сделок (у корзины графика нет «строк» для мини-отчёта).
- Вкладка «Конструктор» вне охвата задачи (там уже есть свой дрилл через
  ReportTable metric-клик, отдельная история).

## Acceptance

1. Клик по корзине/точке любого из трёх графиков открывает панель со списком
   сделок этой корзины, отфильтрованным активными фильтрами страницы; число
   «Итого» в панели (режим «Все N») совпадает с числом на графике.
2. Переключатель «Все/Продано» меняет список и совпадает со вторым числом
   тултипа.
3. Колонки, ссылка на Bitrix, сортировка, обрезка `LIMIT 1000` — те же, что в
   существующем дрилл-дауне отчётов (компонент переиспользован, не
   продублирован).
4. `npm run typecheck` и `npm run build` зелёные.
