# Спека: четвёртый график «В работе → продажа по дням»

Задача 2553. Владелец (Серёга) прислал скриншот ВТОРОГО графика раздела
«Графики» («Вероятность продажи от дней в работе, стадии WORK») с подписью:
«Вот этот график по аналогии с третьим добавь ещё пж».

## Трактовка

Координатор передал владельцу параллельно, здесь фиксирую как принятую (данные
подтвердили сходимость — см. ниже): нужен ЧЕТВЁРТЫЙ график — та же когорта и
те же «дни», что у второго графика (WORK-пресет `stageSurvival.ts`), но в
подаче ТРЕТЬЕГО (life table `calledToSaleCohort.ts`): серые столбики «дожили
минимум N дней в работе, не продав раньше», линия — «продано ровно на день N».
Добавлен РЯДОМ со вторым графиком (сразу под ним), а не вместо него — второй
остаётся с бакетами/CR% как был.

## Ключевое отличие «дня» от третьего графика

Третий график («Созвонился → продажа») считает день как календарные сутки от
входа в стадию до `sold_at`. Здесь день — то, что уже считает `stageSurvival.ts`
для пресета `work`: НАКОПЛЕННОЕ время во всех WORK-стадиях (`SurvivalDealRow.days`
— сумма интервалов «событие WORK-стадии → следующее событие»), НЕ календарные
дни — сделка могла выходить из работы и возвращаться, растягивая календарный
срок сильно дальше, чем накопленное время в работе.

У `SurvivalDealRow.days` уже есть нужное дуальное свойство: для проданной
сделки это финальное значение на момент выхода в `sold`/`shipped` (`work_stages`
их исключает, см. `stageSurvival.ts`), для непроданной — растёт до `now()`.
То есть `days` одновременно служит и «eventDay» (для проданных), и
«observedDays» (право-цензурирование для всех) — та же дуальность, что
`calledToSaleCohort.ts` хранит в двух отдельных полях по календарным дням.

## Реюз, не копия

- **`features/charts/engine/lifeTable.ts`** (новый) — алгоритм раскладки по
  life-table (`buildLifeTablePoints`) и дрилл-даун по дню
  (`selectLifeTableDealIds`) вынесены из `calledToSaleCohort.ts` в общий модуль.
  `calledToSaleCohort.ts` отрефакторен на использование этого модуля (было
  ~40 строк дублирующегося цикла — теперь один вызов). `workDaysCohort.ts`
  использует тот же модуль поверх `SurvivalDealRow` из `stageSurvival.ts`
  (`fetchWorkRows`, экспортирован).
- **UI**: `CalledToSaleCohortChart.tsx` — тот же компонент для обоих графиков
  (получил параметризуемый `axisLabel`, раньше был хардкожен под третий
  график). `ChartsPage.tsx` — `LifeTableCard` (был `CalledToSaleCohortCard`)
  параметризован конфигом (`fetchUrl`/`dealsUrl`/`title`/`description`/
  `accent`/`axisLabel`), инстанс на каждый график вместо двух копий карточки.
- **Дрилл-даун** (задача 2546) работает на новом графике «из коробки» — новые
  роуты `POST /api/charts/work-days-cohort` и `/api/charts/work-days-cohort/deals`
  написаны 1-в-1 по образцу `.../called-to-sale-cohort[/deals]`, гидрация через
  тот же `lib/reports/dealsByIds.ts`.

## Сходимость (проверено на живых данных)

Одинаковые фильтры (период 03.04–29.07.2026, первичные, все клиенты, все
отделы, Категория КЦ): `/api/charts/stage-survival` (preset=work) и
`/api/charts/work-days-cohort` дали **идентичные** `cohortTotal`/`soldTotal`/
`overallPct`: `36254 / 5426 / 15%` в обоих ответах (значения на грани
допустимого дрейфа живых прод-данных между двумя последовательными запросами
— в скриншотах на секунду позже видно `36257`/`36258`/`36261`, счётчик растёт
в реальном времени, не расхождение движков).
