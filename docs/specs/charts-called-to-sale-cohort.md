# Спека: «Графики» — третий график, когорта «Созвонился → продажа по дням»

Задача 2533. Владелец (Серёга), дословно: «нужен третий кастомный график, который
показывает сколько всего было сделок в статусе "Созвонился..." и сколько их них
всех в какой день по счету продается. То есть я хочу увидеть, что допустим за
период было в этом статусе всего 100 сделок как минимум 0 дней и из них 15 продаж,
как минимум 1 день и из них же 10 продаж и так далее.»

## Цель

Life-table (таблица дожития) по дням от входа в стадию «Созвонился и озвучил
цены» до фактической продажи. Отвечает на вопрос «на какой день после созвона
случается продажа» — доп. разрез к уже существующим кривым выживаемости.

## Метрика

- **Когорта** — сделки, впервые вошедшие в стадию `stages.name ILIKE 'Созвонился и
  озвучил%'` в выбранном периоде. Вход определяется по `sa.deal_events`
  (`MIN(event_at)` на сделку в целевых стадиях), НЕ по текущему `deals.stage_id`.
  Тот же резолвинг стадии и та же семантика когорты, что в существующем
  `stageSurvival.ts` (пресет `priced`) и `calledConversion.ts`.
- **Продажа** — `deals.sold_at IS NOT NULL AND sold_at >= first_at`. Тот же паттерн
  защиты от известного дефекта («`sold_at`/`lost_at` пишутся один раз, не
  обновляются при повторном входе в стадию») что уже используется в
  `stageSurvival.ts` и `calledConversion.ts`: сравнение с `first_at` текущей
  когорты отсекает продажи от прошлого цикла сделки, случившиеся ДО входа.
  Полноценно счётчик циклов не решает баг (если сделка продавалась, потом
  вернулась и продалась снова в течение одного и того же периода когорты —
  `sold_at` не различит два события), но это тот же остаточный риск, что и в
  уже принятом владельцем графике «Вероятность продажи».
- **День N** считается от `first_at` (вход в стадию), НЕ от `exit_at` (выход из
  стадии, как в существующей кривой survival) — здесь именно «до продажи», по
  буквальной формулировке владельца.
  - `eventDay` (только для проданных) = `floor(sold_at − first_at)` в днях.
  - `observedDays` = `eventDay`, если продана; иначе `floor(now() − first_at)`
    (сколько дней уже наблюдаем непроданную сделку).
- **cohortAtLeastN** («дожили минимум N дней, не продав раньше») = число сделок
  когорты с `observedDays >= N`.
- **soldOnDayN** = число сделок с `eventDay == N`.
- Диапазон: дни `0..30` поштучно, `31+` — агрегированная точка
  (`cohort = observedDays>=31`, `sold = eventDay>=31`).
- Инварианты для сверки: `cohortAtLeastN` монотонно не возрастает по N;
  `Σ soldOnDayN <= cohortTotal`; `cohortAtLeast0 == cohortTotal`.

## Edge cases

- Весь период раньше `DEAL_EVENTS_DATA_START` (03.04.2026) → `null`, карточка
  показывает «история стадий ещё не велась» (как у двух существующих графиков).
- Пустая когорта (нет сделок под фильтры) → «нет сделок под выбранные фильтры».
- Сделка ещё не продана и ещё в стадии/уже вышла из неё в другую — не исключается
  из когорты, просто не даёт `soldOnDayN` ни на одном дне, но входит в
  `cohortAtLeastN` пока `observedDays >= N` (право-цензурирование, стандартно для
  таблиц дожития).

## API-контракт

`POST /api/charts/called-to-sale-cohort` — тот же паттерн, что
`/api/charts/stage-survival`, право `section.charts`.

Body: `{ period: {from,to}, dealScope?, clientType?, departmentIds?,
productGroupMode?, productGroupIds? }`.

Response: `{ result: CalledToSaleCohortResult | null }`, где
```
interface CalledToSaleCohortPoint { day: number; label: string; cohort: number; sold: number; pct: number|null }
interface CalledToSaleCohortResult { points: CalledToSaleCohortPoint[]; cohortTotal: number; soldTotal: number; overallPct: number|null }
```

## Реализация (переиспользование)

- `features/charts/engine/calledToSaleCohort.ts` — новый файл. SQL повторяет
  `target_stages`/`first_entry`/`cohort` CTE из `stageSurvival.ts` (та же стадия,
  тот же период), но вместо `exit_event` выбирает `d.sold_at`. Переиспользует
  `scopeWhere`/`departmentsWhere` (экспортированы из `stageSurvival.ts`),
  `buildProductGroupFilter`, `toSqlInterval`/`periodDateStrFromInstant`/
  `DEAL_EVENTS_DATA_START`.
- `app/api/charts/called-to-sale-cohort/route.ts` — копия структуры
  `stage-survival/route.ts` без параметра `preset`.
- `features/charts/ui/CalledToSaleCohortChart.tsx` — recharts `ComposedChart` в
  том же визуальном языке, что `SurvivalChart.tsx`: серые бары `cohort` на
  скрытой оси (чувство масштаба когорты по дням), линия `sold` (абсолютное число
  продаж в этот день) на видимой оси. Тултип: день, когорта, продано, `sold/cohort%`.
- `features/charts/ui/ChartsPage.tsx` — третья карточка под двумя существующими,
  на вкладке «Вероятность продажи», те же общие фильтры (период/отдел/воронка/
  тип клиента/товарные группы), тот же `useQuery`-паттерн.

## Что НЕ делаем

- Никаких миграций БД — метрика не персистится, состояние только в React.
- Никакой новой роли/права — используем существующее `section.charts`.
- Никакого счётчика «циклов» сделки (повторный вход в стадию после возврата) —
  берём только первый вход, как и существующий survival-график.
- БД только на чтение, деплой/пуш в `dev-asteroid`/`main` не делаем — только
  ветка `feat/charts-called-to-sale-cohort` в `origin` для владельца.

## Открытые вопросы владельцу

1. Подтвердить: «день продажи» = день относительно ВХОДА в «Созвонился…», а не
   относительно выхода из этой стадии (в проекте несколько WORK-стадий между
   «Созвонился» и «Продано», сделка может провести там дни независимо от
   созвона) — трактовка отправлена владельцу заранее в задаче, возражений не было.
2. Устраивает ли право-цензурирование (сделки без продажи учитываются в когорте
   только пока наблюдались минимум N дней) — альтернатива «включать все N
   бессрочно» завышала бы знаменатель для дальних дней свежими сделками.
